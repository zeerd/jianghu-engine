# Instructions / Rules 编写规范

> **指令文件是稳定的「行为合同」，不是事实仓库。**
> 它只规定每次运行都必须遵守的稳定规则；易变事实、工具语义、边缘逻辑与基础设施约束，交给对应层承载。

---

## 1. 必须写的内容

每份指令文件必须包含：

- **YAML frontmatter**：`name`、`description`（做什么与何时应用）、`applyTo` 触发范围。
- **可执行的行为规则与决策启发式**，允许且仅允许五类：
  1. 命令与调用方式（怎么跑 / 怎么调试，不带参数清单）；
  2. 纪律与决策启发式（必须 / 禁止、何时做什么）；
  3. 排查表（症状 → 动作）；
  4. 完成标准与提交清单；
  5. 指针（配「先读它」的动作）。
- **指向设计文档的「为什么」指针**（`见 design §X` 形式）。

表达要求：使用正向、具体的事实陈述（「用 X」「从不 Y」），而非请求式措辞（「请不要 Y」）；
每条规则都应能对应到具体行为或评估案例；一句话因果帮执行纪律可留，成段论证不可留。

---

## 2. 禁止写的内容及正确归属

| 禁止写入指令文件的内容 | 实际归属 |
|---|---|
| 成段论证（为什么这么设计、取舍对比） | `docs/design/`，指令侧留一行指针 |
| 机制与架构叙述 | `docs/design/`，指令侧留一行指针 |
| 沿革（事故时间线、日期、批次） | `docs/design/`，指令侧留一行指针 |
| 实测数据（耗时地板、行号） | `docs/design/`，指令侧留一行指针 |
| 与设计文档逐字重复的句子 | 同一句话只许存在一处，另一处是指针 |
| 会漂的事实数字的第二份拷贝（道数、默认值、参数表、清单、示例输出） | 源头（脚本 / CLI / 设计文档），指令文件教去哪看 |
| 用户问题、会话历史、时间戳、请求 ID | 用户消息 / 最新用户轮次 |
| 工具名称、参数、Schema、工具使用说明 | 工具定义本身（签名 / `Description()` / Schema） |
| if-else 分支、重试逻辑、异常处理 | 工具逻辑 / 编排代码 |
| 速率限制、鉴权、计费、访问控制 | 基础设施层 / 网关 / 中间件 |
| 通用且不改变行为的 LLM 指令（「要乐于助人」） | 删除，除非它确实改变行为 |
| 语调与风格的形容词墙 | 少量代表性输入-输出示例 |
| 详细风格指南、词汇表 | 独立引用文件，由指令文件指向 |
| 项目专属的一次性命令、文件位置、目录结构 | 项目导航层（`AGENTS.md`） |
| 仅本次请求生效的任务指令 | 最新用户轮次 |
| 对不在上下文中的文件的指代式引用 | 改为明确、自包含的规则 |

**清单不进指令文件**：参数表、DSL 动词 / 条件表、道清单、资源清单这类「加一条要改文档」的清单，归设计文档维护（源头是脚本 / CLI 时以源头为准）——指令文件教去哪看、怎么用，不替人维护清单。**发现自己正往指令文件里「加一行表」，就是改动入口放错了地方。**

**计划书与阶段工具一律不引用**：计划书是任务清单、用完即删，不是长期文档。

## 3. 内容分层原则

1. **指令层**：稳定的行为契约。
2. **运行时层**：用户问题、文件内容、上下文、时间戳等动态输入。
3. **工具层**：工具描述、参数、Schema、工具执行逻辑。
4. **代码 / 编排层**：边缘情况、重试、异常处理。
5. **基础设施层**：速率限制、鉴权、计费、访问控制。
6. **项目导航层**：`AGENTS.md` 中的构建命令、目录结构、文件位置。
7. **模块化规则层**：`.claude/rules/` 中按主题拆分的可复用规范。

判断标准：

> 每次请求都会变化的内容，不属于 instructions。
> 删除后没有任何具体评估案例变差的规则，是噪声，删除或合并。
> 能靠工具或代码保证的规则，移到工具或代码层。

---

## 4. 交付前自检

完成一份指令文件后，逐项检查：

- [ ] frontmatter 三件（`name` / `description` / `applyTo`）齐全，description 说明何时应用。
- [ ] 是否存在每次请求都会逐字节变化的内容？有 → 移到运行时。
- [ ] 是否存在删除后不会让任何具体评估案例变差的规则？有 → 删除或合并。
- [ ] 是否存在可由工具或代码保证的规则？有 → 移到工具层或代码层。
- [ ] 是否重复声明了工具名称、参数或 Schema？有 → 删除。
- [ ] 是否使用「不要……」等请求式措辞？有 → 改为正向、具体的事实陈述。
- [ ] 是否把项目命令、目录结构写进了指令文件？有 → 移到项目导航层。
- [ ] 是否内联了可复用规范或往里加清单表？有 → 拆出 / 归源。
- [ ] 是否引用了不在上下文中的文件？有 → 改为自包含规则或提供文件内容。
- [ ] **自测题**：这段是让人「照着做」，还是让人「读了懂」？「读了懂」成段（论证 / 机制 / 沿革 / 实测数据）→ 移入 `docs/design/` 留指针；一句话因果帮执行纪律 → 可留。
- [ ] 与 `docs/design/*.md` 对句查重：同一句话只许存在一处，另一处是指针。
- [ ] 同一改动涉及两文档时：设计进 `docs/design/`、操作变化进指令文件 / 技能，禁止把设计段落整段贴进指令文件。
- [ ] 指令文件与设计文档同步改过之后，交叉指针（design §X ↔ 指令 §Y）逐个核对仍然成立。

---

## 5. 维护规则

- 以评估案例驱动增删规则；新规则只有在能改变具体行为或修复具体失败案例时才加入。
- 动态事实、工具语义、边缘逻辑和基础设施约束不得回流到 instructions。
- 主文件保持短小；可复用规范按主题拆分为模块化文件。
- 项目导航信息放入 `AGENTS.md`，不放入指令文件。
- 任务特定指令放入最新用户轮次，不放入系统提示。
