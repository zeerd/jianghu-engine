# Instructions / Rules 编写规范

## 1. 目的与适用范围

本规范用于指导编写或审查 AI 系统提示、项目规则文件、Agent/工具 instructions 等规则文本。

编写 instructions 时，必须遵循一个核心原则：

> **Instructions 是稳定的“行为合同”，不是事实仓库。**
> 它只规定每次运行都必须遵守的稳定规则；易变事实、工具语义、边缘逻辑和基础设施约束，应交给对应层承载。

本规范适用于 Claude Code、Cursor、Codex、云平台 AI 服务等场景下的 instructions/rules 编写。它不是单一机构颁布的强制标准，而是主流实践形成的高度重叠共识。

---

## 2. 必须写的内容

一份 instructions 只应包含稳定、静态、不随单次请求变化的内容。通常限定为以下 5 类。

### 2.1 角色与使命

用 1–2 句话定义“它是谁、为什么存在、负责什么”，形容词一律省略。

示例：

```markdown
你是 Support Triage Drafter，负责起草订单状态回复，并将结果放入人工审核队列。
```

### 2.2 不变量与硬性规则

写明无论用户问什么，都永远为真或永远禁止的行为。

要求：

- 使用事实陈述，例如“你从不直接发送邮件”，而不是请求式措辞“请不要直接发送邮件”。
- 使用正向、具体的指令，例如“用 X”，而不是“不要 Y”。
- 每条规则都应能对应到具体行为或评估案例。

示例：

```markdown
你从不直接发送邮件，只将回复写入审核队列。
未经人工批准，绝不执行写操作。
```

### 2.3 决策启发式

写明在什么条件下应澄清、升级、停止或选择某一动作。

示例：

```markdown
如果用户请求超出订单范围，升级处理。
如果缺少必要字段，先向用户澄清，不要猜测。
```

### 2.4 输出格式与完成标准

写明最终答案的结构、长度、必须包含的字段，以及“做到什么程度算完成”。

示例：

```markdown
返回 JSON，包含 `status`、`summary`、`next_action` 三个字段。
```

### 2.5 安全与操作边界

写明操作约束、权限边界和升级条件。

示例：

```markdown
调用工具总数不超过 5 个；超过则升级。
未经人工批准，不得执行写操作。
```

### 2.6 表达与组织要求

编写 instructions 时：

- 使用 Markdown 或 XML 标签划分区块，例如 `<role>`、`<rules>`。
- 保持短小、清晰、可执行。
- 只保留会改变行为的规则。
- 优先使用少量代表性示例展示语气和格式，而不是使用“专业、友好、共情”等形容词墙。
- 大段风格指南、术语表、供应商列表应放入独立引用文件，不要内联到主 instructions。

## 3. 禁止写的内容及正确归属

以下内容不得写入 instructions。每项内容都应迁移到正确层级。

| 禁止写入 instructions 的内容 | 实际应写在哪里 |
|---|---|
| 用户具体问题、当前文件内容、屏幕上下文、会话历史、时间戳、请求 ID | 用户消息 / 运行时 payload |
| 工具名称、参数、Schema、工具使用说明 | 工具定义本身，例如函数签名、`Description()`、`Parameters()`、JSON Schema |
| if-else 分支、重试逻辑、异常处理、边缘情况逻辑 | 工具逻辑 / 编排代码 |
| 速率限制、鉴权、计费、访问控制 | 基础设施层 / 工具层 / 网关 / 中间件 |
| 通用且不改变行为的 LLM 指令，例如“要乐于助人”“请保持礼貌” | 删除；除非该领域确实需要并会改变行为 |
| 语调与风格的形容词墙 | 少量代表性输入-输出示例 |
| 详细风格指南、词汇表、供应商列表 | 独立引用文件，由 instructions 指向 |
| 项目专属的一次性命令、文件位置、目录结构 | `CLAUDE.md` / `AGENTS.md` |
| 可复用的格式化约定、架构模式、提交规范 | `.claude/rules/` 或 `.cursor/rules/` 等模块化规则文件 |
| 仅本次请求生效的任务指令 | 最新用户轮次，而不是系统提示 |
| 对不在上下文中的文件的指代式引用，例如“按照 `config.py` 里的 schema 来” | 将文件内容放入上下文，或改为明确、自包含的规则 |

---

## 4. 内容分层原则

编写或审查 instructions 时，必须按以下层级划分责任：

1. **Instructions 层**：稳定的行为契约。
2. **运行时层**：用户问题、文件内容、上下文、时间戳等动态输入。
3. **工具层**：工具描述、参数、Schema、工具执行逻辑。
4. **代码/编排层**：边缘情况、重试、异常处理。
5. **基础设施层**：速率限制、鉴权、计费、访问控制。
6. **项目导航层**：`CLAUDE.md` / `AGENTS.md` 中的构建命令、目录结构、文件位置。
7. **模块化规则层**：`.claude/rules/` 或 `.cursor/rules/` 中的可复用规范。

判断标准：

> 如果一段内容每次请求都会变化，它不属于 instructions。
> 如果一条规则删除后没有任何具体评估案例变差，它可能是噪声。
> 如果一条规则可以靠工具或代码保证，就把它移到工具或代码层。

---

## 5. 推荐文档结构

编写 instructions 文件时，优先使用以下结构：

```markdown
# <名称>

## 角色与使命
<1–2 句话>

## 不变量与硬性规则
- <永远为真的规则>
- <永远禁止的行为>

## 决策启发式
- 当 <条件> 时，执行 <动作>。
- 当 <条件> 时，升级处理。

## 输出格式与完成标准
<结构、字段、长度、完成条件>

## 安全与操作边界
- <权限边界>
- <升级条件>
- <工具调用上限>
```

要求：

- 每个区块只承载一类信息。
- 不重复声明工具 Schema。
- 不内联大段示例。
- 不引用上下文中不存在的文件作为规则依据。
- 整体长度应显著控制在“角色 + 不变量 + 输出格式”所需范围内。

---

## 6. 自检清单

完成 instructions 后，必须逐项检查：

- [ ] 是否存在每次请求都会逐字节变化的内容？如果有，移到运行时。
- [ ] 是否存在删除后不会让任何具体评估案例变差的规则？如果有，删除或合并。
- [ ] 是否存在可由工具或代码保证的规则？如果有，移到工具层或代码层。
- [ ] 是否重复声明了工具名称、参数或 Schema？如果有，删除。
- [ ] 是否引用了不在上下文中的文件？如果有，改为自包含规则或提供文件内容。
- [ ] 是否使用“不要……”等请求式措辞？如果有，改为正向、具体的事实陈述。
- [ ] 是否用形容词堆砌语气要求？如果有，改为少量代表性示例。
- [ ] 是否把项目命令、目录结构写进主 instructions？如果有，移到 `CLAUDE.md` / `AGENTS.md`。
- [ ] 是否把可复用规范内联在主文件？如果有，拆分到 `.claude/rules/` 或 `.cursor/rules/`。
- [ ] 整体是否只包含“角色 + 不变量 + 决策启发式 + 输出格式 + 安全边界”？如果不是，精简。

---

## 7. 维护规则

维护 instructions 时：

- 以评估案例驱动增删规则。
- 新规则只有在能改变具体行为或修复具体失败案例时才加入。
- 动态事实、工具语义、边缘逻辑和基础设施约束不得回流到 instructions。
- 主文件保持短小；可复用规则按主题拆分为模块化文件。
- 项目导航信息放入项目级文件，不放入系统级 instructions。
- 任务特定指令放入最新用户轮次，不放入系统提示。

---

## 8. 核心结论

Instructions 只负责“稳定的行为合同”。

动态事实归运行时，工具语义归工具定义，边缘逻辑归代码，基础设施约束归基础设施，项目导航归项目文件，可复用规范归模块化规则文件。

把不该写的内容迁移到正确层级后，instructions 应自然变得短小、清晰、可执行。
