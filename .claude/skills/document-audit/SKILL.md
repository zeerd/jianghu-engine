# 工程文档体系审计与重构

**适用场景**：工程内 AGENT 文件、指令文件、技能文件、设计文档、代码、工程文件之间存在职责混杂、循环引用、反向引用或内容错位，需要系统性梳理。

本文档中 **MUST**、**MUST NOT**、**SHOULD**、**SHOULD NOT**、**MAY** 按 RFC 2119 解释：MUST / MUST NOT 为绝对要求或绝对禁止，不合规即为缺陷；SHOULD / SHOULD NOT 为推荐或推荐避免，偏离时需要记录理由。


## 一、为什么 AI 会被现有文档“说服”

AI 默认倾向于把工程内**已经存在的结构**当作合理基线。当设计文档写着“参考技能文件 xxxxx”，AI 读到这条引用时，会倾向于认为“设计文档本来就该引用技能文件”，而不是问“设计文档**凭什么**引用技能文件”。

要打破这个循环，审计代理在开始任何梳理之前 **MUST** 先接受以下两条元规则：

**元规则 1：职责先于引用。** 一份文档允许引用什么，取决于它**自身被允许承载什么**，不取决于它当前引用了什么。一份设计文档引用了技能文件，不能证明这个引用合理；只能证明这份设计文档**可能已经越界**。

**元规则 2：引用方向必须形成无环有向图。** 文档之间的依赖必须单向流动；任何 A → B → … → A 的路径都是缺陷，无论环上每一份文档的内容看起来多么“自洽”。


## 二、文档分层：每类文档的权威边界

当前工程中各类文档的混用，根源在于没有把“**行为约束**”“**可执行流程**”“**设计意图**”“**阶段产物**”拆开。收敛为多层分工：AGENT 文件与指令文件管行为层（常驻、无条件生效），SKILL.md 管可复用任务的工作流，设计文档管系统的规范性意图与边界，计划书与阶段工具是随阶段失效的产物，共享设施文档服务技能。以下逐类给出“必须有什么”和“禁止有什么”。

### 2.1 AGENT 文件（AGENTS.md 或等价主指令文件）

**定位**：项目级**行为简报**，告诉代理在这个仓库里“怎么做才不会踩雷”。

**MUST 包含**：
- 非标准工具选择（例如用 `uv` 而不是 `pip`）；
- 命令陷阱（例如测试必须加某个 flag）；
- 隐藏约束 / 雷区（例如废弃但仍被生产引用的目录）；
- 无法从代码或配置中自行发现的、对任务成败有实质影响的约定。

**MUST NOT 包含**：
- 技术栈摘要、目录结构总览、架构描述——这些代理读代码和配置就能推断，放进 AGENT 文件会稀释真正不可发现的信息；
- 通用最佳实践（“保持代码整洁”“遵循最佳实践”），因为它们不可执行、不可判定；
- 已被 linter / typecheck / test / CI 强制执行的规则；
- **对技能文件或设计文档的“反向定义”** 。AGENT 文件 **MUST NOT** 用“参考技能文件 xxx 来了解项目结构”这类语句把项目级约束外包给下层文档。

**长度**：SHOULD 控制在 200–500 行以内；超过时 SHOULD 拆分为层级化的 AGENT 文件放在相关模块附近，而非继续膨胀根文件。

### 2.2 技能文件（SKILL.md 或等价可执行任务单元）

**定位**：**可复用、可执行的任务工作流**，回答“这类任务具体按什么步骤做”。

**MUST 包含**：
- YAML frontmatter：`name`（与文件夹名一致）和 `description`（说明“做什么”和“何时使用”）；
- 可执行的工作流步骤，最好带 checklist 或验证循环（validate → fix → re-run）；
- 具体的、可运行的示例或脚本入口。

**MUST NOT 包含**：
- 复述性辅助文件——内容与工作流无关或只是重复说明的文档（README.md、CHANGELOG.md 等）放在技能文件夹内；文档细节应进入 `references/`。技能运行所需资产（许可证、`scripts/`、`agents/`、模板、评估用例）不算辅助文件；
- 对 AGENT 文件或设计文档的**反向规约**。技能文件 **MUST NOT** 规定“项目级规则见 AGENTS.md 第 x 节”——技能文件是执行层，不是项目治理层；
- 时敏信息（除非被隔离在明确的“旧模式”块中）和魔数常量。

**引用规则（关键）** ：SKILL.md 中引用其他文件时， **MUST 使用相对于技能根目录的路径**，且 **MUST 保持引用深度不超过一层**（`references/REFERENCE.md` 可以，`references/a/b/c.md` 不行）。这条规则直接防止技能文件成为循环引用的中转站。

**长度**：SKILL.md 本体 SHOULD 在 500 行 / 约 5k tokens 以内；重内容 **MUST** 移入 `references/`、`scripts/`、`assets/`。

### 2.3 设计文档（Design Doc / 设计文档）

**定位**：**一个系统**的持久意图声明——系统用来做什么、核心词是什么意思、什么必须永远成立、什么被刻意排除在外。设计文档是**规范性**的，但不执行具体流程。

**MUST 满足（红线，违反即 FAIL）**：
- **自包含**：规范性内容直接写在自身；缺规范就补进自身，不降格为对其他文档的引用；
- **禁止实现代码、脚本或具体实现逻辑**；接口章节仅定义签名与行为契约，严禁实现逻辑；
- **禁止对技能文件的操作性引用**——设计文档 **MUST NOT** 出现"参考技能文件 xxxxx"这类语句，不允许把规范性内容降格为"去某个技能文件里找"；
- **禁止对 AGENT 文件的规范性引用**——设计文档的权威性来自自身内容，不来自 AGENT 文件。

**SHOULD 包含（结构模板；缺失时记录偏离理由，不判 FAIL）**：
- **Purpose**：一段话说明系统为何存在、为谁服务；超过两段通常意味着系统边界本身有问题；
- **Glossary / 术语表**：核心术语的一行定义，以及"应避免"的误用别名；**零实现细节**，出现类名或表名即视为泄漏；
- **Invariants / 不变量**：编号、可测试；审阅者看着一个 diff 必须能回答"是否仍然成立"；
- **Boundaries & Non-goals**：明确不做什么，以及被拒绝的范围和拒绝理由；
- **Interfaces / Seams**：高层交互面，只写名称和责任，不写签名；
- **Decision log**：仅记录难以逆转、反直觉或真实权衡的决策；日常选择不应进入。

**生命周期**：设计文档是**活文档**，就地修订，**MUST NOT** 用新的带日期文件取代旧文件。

### 2.4 指令文件（仓库常驻规则层的模块化规则，如 `*.instructions.md`）

**定位**：按主题拆分的**常驻行为规则**，与 AGENT 文件同属行为层，每次运行无条件生效。

**MUST 包含**：YAML frontmatter（`name`、`description` 说明做什么与何时应用、`applyTo` 触发范围）；可执行的行为规则与决策启发式；指向设计文档的「为什么」指针。

**MUST NOT 包含**：成段论证、机制叙述、沿革与实测数据（进设计文档，指令侧留一行指针）；会漂移的事实数字的第二份拷贝（清单归源头——脚本、CLI、设计文档，指令文件教去哪看）；对计划书与阶段工具的引用。

### 2.5 计划书、阶段工具与裁定台账

- **计划书**（任务清单）：只放待办条目、勾选与一行运行记录，批次收口即删；**MUST NOT** 被任何正式文档引用。
- **阶段工具**（认领清单、未命中清单）：只服务当前阶段，阶段收口后删除；**MUST NOT** 被设计文档引用。
- **裁定/证据台账**：记录会被后来读者需要的裁定依据与证据（公式推导、实测数据、重开条件），归属**设计层**、放设计文档目录，作为设计文档的溯源性引用目标；**MUST NOT** 放在计划书目录。
- 三者归属按 §3.2 归属判据裁定：待办执行 → 计划书；随阶段失效 → 阶段工具；随系统存续且被后来读者需要 → 裁定台账（设计层）。

### 2.6 共享设施文档（技能共用的说明、配置与模板目录）

- **MUST** 只引用仓库内实际存在的文件；
- 引用未随包落地的外部资产时，**MUST** 在引入处注明「以仓库实际存在的文件为准」。


## 三、引用方向：强制单向，禁止循环

仅有内容边界还不够。你遇到的核心问题是引用本身形成了闭环。审计代理 **MUST** 按以下方向规则重建引用图。

### 3.0 判定前提：先分类，再判向

对第 2 步提取的每一条引用，审计代理 **MUST** 先分为两类，再按 §3.1 判定：

- **规范性引用**：目标文档是源文档正确性的必要条件——删除后源文档的结论或流程不再成立。按 §3.1 白名单判方向。
- **溯源性引用**：目标文档只提供背景、证据或导航——删除后源文档仍成立。不判方向，只判两条：**锚点是否稳定**（能定位到文件/节/条目）；**目标是否被当成唯一规范来源**（是则升格为规范性引用，按白名单判）。

§3.1 白名单约束的是规范性引用；溯源性引用即使指向白名单外的目标也合法，但被当成唯一依据即违规。

### 3.1 允许的引用方向（白名单，约束规范性引用）

| 源文档 | MAY 引用 | MUST NOT 引用 |
|---|---|---|
| **AGENT 文件** | 技能文件（仅限“何时触发某技能”，不得用于定义项目规则）；代码/配置文件路径 | 设计文档（项目级行为不依赖设计意图来定义） |
| **指令文件** | 设计文档（「为什么」指针）；代码/配置文件路径 | 计划书与阶段工具；技能文件正文（触发入口除外） |
| **技能文件** | 同一技能内的 `references/`、`scripts/`、`assets/`（一层深度）；代码/配置文件路径 | AGENT 文件；指令文件；设计文档；其他技能文件（跨技能引用 MUST 经过 AGENT 文件或独立编排层，不得直接互引） |
| **设计文档** | 溯源性引用（背景、证据、导航；锚点须稳定）。规范性内容 **MUST** 自包含 | 技能文件、AGENT 文件、其他设计文档的**规范性引用** |
| **代码/工程文件** | 在注释中以稳定锚点引用设计文档的 Invariant / Decision 条目，用于解释 why；依赖工程制品（schema、配置、生成物） | 在行为、构建、测试、运行时上依赖任何 AGENT / 指令 / 技能 / 设计文档；把文档作为某条不变量的唯一规范来源 |

**关键**：设计文档 **MUST NOT** 把技能文件当作规范来源。工程中“设计文档参考技能文件 xxxxx”正是典型的**反向引用**——执行层被用来定义规范层，方向完全颠倒（此类引用属规范性引用，按白名单判非法）。设计文档如果缺少某条规范， **MUST** 直接把该规范写进自身；如果该规范属于可执行流程，那它本来就不应该出现在设计文档的引用范围内。

### 3.2 循环引用的判定与归属裁定

审计代理 **MUST** 将全部文档视为有向图的节点，每条“引用”视为有向边，运行一次环检测。任何长度 ≥ 2 的环（A → B → A）或自环（A → A）都是 **MUST FIX** 缺陷。

断环的唯一合法方式是**提升权威到正确的层**：如果 A 和 B 互相需要对方的内容，说明它们之间的职责边界错了。 **MUST NOT** 通过“在两边各写一份”或“加一个索引文件”来掩盖环；**MUST** 判断哪一层才是该内容的权威层，将内容上移或下移，然后删除反向边。

**归属判据**（判定「正确的层」在哪，代理据此裁定，**MUST NOT** 外推给人工）：
- 内容**每次运行都必须遵守** → 行为层（AGENT 文件 / 指令文件）；
- 内容**按步骤执行** → 技能层；
- 内容**随系统存续且被后来读者需要** → 设计层（含裁定/证据台账）；
- 内容**随阶段或批次失效** → 阶段层（计划书、阶段工具，收口删除）。
- 归属裁定的理由与备选方案 **MUST** 记录在审计报告中。


## 四、AI 审计执行流程

审计代理 **MUST** 按以下顺序操作，不得跳过或并行。

### 第 0 步：冻结“当前结构合理性”判断

在读取任何文档内容之前，审计代理 **MUST** 先声明：

> “当前工程中文档之间的引用关系**不构成**任何证据，证明该引用是合理的。所有引用将在第 3 步中按本技能的方向白名单独立判定。”

这一步是防止 AI 被绕晕的操作性前提。

### 第 1 步：逐文档做“内容归属审计”

对每一份文档，**MUST** 只依据第二节的 MUST / MUST NOT 清单逐条检查，**不得**参考其他文档来“理解”该文档的合理性。

输出格式：

```
文档：<路径>
类型：AGENT / 指令文件 / 技能 / 设计文档 / 计划书 / 阶段工具 / 裁定台账 / 共享设施 / 其他
越界项：
  - [MUST NOT 违规] 具体行/段落，违反了哪一条
缺失项：
  - [SHOULD 缺失] 缺少哪一项（不判 FAIL，附偏离理由）
判定：PASS / FAIL
```

**关键约束**：审计某份文档时， **MUST NOT** 把“它引用了什么”作为判断依据。内容归属先于引用审计。

### 第 2 步：提取引用图

从全部文档中提取每一条指向工程内其他文档/文件的引用，构建有向边列表：

```
源 → 目标 | 源类型 | 目标类型 | 引用语句摘要
```

**MUST** 包含所有形式的引用：Markdown 链接、裸路径、“参见/参考/详见”类语句、YAML frontmatter 中的路径。

### 第 3 步：方向合法性判定与环检测

3a. 对第 2 步的每一条边，先按 §3.0 分类（规范性 / 溯源性）：规范性边按 §3.1 白名单判定，溯源性边按 §3.0 的两条判。输出：合法 / 非法 / 需人工复核。

3b. 在全部边上运行环检测（拓扑排序或 DFS）。输出：

```
环 1：A → B → C → A
环上节点：A（设计文档），B（技能文件），C（AGENT 文件）
断环建议：将 B→C 的引用提升为 … / 将 C→A 的引用删除并上移至 …
```

3c. **任何环 MUST 被报告，MUST NOT 被静默忽略或自动“合理化”** 。如果 AI 发现自己在为某个环寻找“其实也说得通”的理由，它 **MUST** 停止并记录为“审计代理试图合理化缺陷”，然后继续按规则判定。

### 第 4 步：输出重构方案并执行改写

审计代理 **MUST** 先输出完整的问题清单和断环/归属修正方案，再按下述口径改写：

- **无歧义的 MUST FIX**（悬空引用、陈旧事实、断环所需的反向边删除、frontmatter 约定对齐）：直接修正，在报告中列明；
- **归属裁定**（内容上移/下移、文件移动）：按 §3.2 归属判据由代理裁定并记录理由与备选方案，**MUST NOT** 以「需人工确认」为由悬置或外推；
- **仅当用户未授权改写**时，整份方案待人工确认后才执行。

方案中每一项 **MUST** 标注：

- 问题类型：内容越界 / 内容缺失 / 非法引用 / 循环引用 / 反向引用；
- 违反的规范条款（第 2 节或第 3 节的具体条目）；
- 建议动作：删除 / 上移 / 下移 / 改写为自包含；
- 动作后的预期引用方向。

### 第 5 步：改写后的复检

改写完成后， **MUST** 重新执行第 1–3 步。复检通过的标准不是“读起来通顺”，而是：

- 每份文档的内容归属审计全部 PASS；
- 引用图中不存在白名单之外的**规范性**边；溯源性边全部满足 §3.0 的两条（锚点稳定、非唯一规范来源）；
- 环检测输出为零。

**MUST NOT** 以“文档之间看起来协调”作为验收标准；**MUST** 以本技能的条款和图的数学性质作为唯一判据。


## 五、附则：审计代理的自我约束

1. **禁止从工程内部寻找规范依据。** 审计过程中，代理 **MUST NOT** 引用工程内任何文档来证明某个结构“应该如此”。唯一可引用的外部依据是本技能。
2. **遇矛盾先记录，不调和。** 如果两份文档对同一事项说法冲突，代理 **MUST** 记录为“跨文档冲突”，并按第 3 步的方向规则判断哪一份越界， **MUST NOT** 试图写一段新文字把两者“融合”起来。
3. **设计文档的自包含性是硬约束。** 一份设计文档如果必须读技能文件才能理解，它的审计结论 **MUST** 是 FAIL，无论其文字多流畅。
4. **AGENT 文件的“少即是多”是硬约束。** 向 AGENT 文件添加内容的默认操作是拒绝；每增加一行，代理 **MUST** 能回答：“这一行在代码/配置/README 中不可发现，且对任务成败有实质影响。” 不能回答，就 **MUST NOT** 添加。
