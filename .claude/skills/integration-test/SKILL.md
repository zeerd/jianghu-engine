# 集成测试（E2E）（integration-test）

本技能是集成测试的**操作规程**：怎么跑、怎么写剧本、断言纪律、怎么排查。
架构、道模型、关键契约、覆盖率口径等设计内容见 `docs/design/integration-test.md`。

## 4. 运行方式

### 4.1 标准运行（完整流程含覆盖率）

```powershell
# 仓库根目录执行
.\run-integration-tests.ps1
```

**脚本自动完成**「构建 → 覆盖率起服 → 并行注册与各道 → persist/reload 双试验台（与各道
并行）→ 优雅关服 → 多路覆盖率合并导出 → 控制台报告」。**逐步行为是脚本与设计的事实，
本技能不复述**：分步清单读脚本文首注释与 `docs/design/integration-test.md`
§1；失败判定四通道见其 §1.4。运行入口就这一条命令，完整跑 = 含覆盖率的验收轮。

### 4.2 运行参数（指针）

**参数清单见 design §1.7**——唯一登记处是脚本 `param` 块，本技能不维护参数表。
新增/修改参数只改脚本 `param` 与 design §1.7；要查有什么参数、取值多少，**先读
design §1.7**，再需要时核对脚本。

### 4.3 调试单个剧本

```powershell
# 快速跑一轮（不出覆盖率）；改过 cli\src 后必须重新构建——加 -SkipBuild 会用旧 CLI
.\run-integration-tests.ps1 -NoCoverage

# 手动跑单个片段：先看 lane_*.sce 里要哪些前置，再复用注册阶段生成的 vars
# （每道一份，在仓库根 test_tmp\e2e_lanes\lane<N>.vars，含 acct/pass）
bin\cli\x64\jianghu_cli.exe --config tests\integration\cli.conf `
  --script tests\integration\scenarios\skill\learn_force.sce `
  --vars test_tmp\e2e_lanes\lane2.vars --report report.txt
```

### 4.4 耗时监控（绝对预算 + Δ 诊断归因）

- **通过标尺是绝对预算 `-DurationBudgetSec`**：超预算高声告警、**不判 FAIL**（预算是
  护栏不是门禁）。报告三行硬指标的字面格式、耗时历史文件、Δ 归因与拆分探索行为，
  全部见 design §2.5；参数值见 design §1.7。
- **每次运行核对三行硬指标**：未超预算、新增场景不落关键路径、吸收能力内；
  **新增场景默认不得进当轮关键路径道**（当轮名单以报告为准，口径见 design §2.5）。
- **Δ 归因仅诊断**，不参与通过判定；抬预算必须改脚本默认值走 diff 评审。
- 拆分道之前必读 §9.4（稀缺资源唯一归属）与 §9.5（`/t` 目标复位）：拆出去的片段若依赖
  钉给原道的资源（清单见 design §2.4），会与并行账号互相踩踏。

### 4.5 服务端日志观测（ERROR 即失败，白名单登记制）

剧本看不见服务端内部报错——**服务端日志是失败判定四通道之一**（机制、run-id 日志文件
命名见 design §1.4；本轮日志的完整路径由报告开头点名，排查直接看它）。判定与登记规则：

| 级别 | 判定 |
|------|------|
| 未登记的 ERROR/FATAL | **整轮 FAIL**（与崩溃 dump 检测同级：剧本全绿但服务端报错同样是矛盾信号） |
| 白名单已登记的 ERROR | 静默，计入报告「白名单吸收 N」 |
| WARN | 仅按函数聚合计数入报告，不判失败（地图边界类告警噪音大） |

**白名单文件** `tests/integration\log-allowlist.txt`：每行 `签名<TAB>归属场景/理由`
（`#` 起头为注释）。签名对「去掉 `[LEVEL] (时间戳)` 前缀后的消息体」做子串匹配，
**必须锚定变量部分**（`wrongpass`、`house_` 等）——只命中预期类、不遮蔽同类真异常
（真丢档/真 DB 故障带不同变量值，照常 FAIL）。

**纪律**：新增负测或任何预期的服务端报错，必须同步登记签名+归属，否则下一轮红；
排查时先看报告的「未登记 N」与完整日志，再决定是登记（预期）还是当生产问题修
（疑似 bug 先查根因，不许直接拉黑——先例见 design §1.4）。

## 9. 编写/维护剧本的规范

### 9.1 新增剧本步骤

1. **先在手工交互模式验证**流程可跑通
2. **记录每一步的服务端输出**（`wait text`/`wait menu` 依赖精确文本）
3. **同步一律用 `wait`**（轮询 + 超时），不靠 `sleep` 赌时序
4. **设置合理 `timeout`**（缺省取 `-StepTimeout`，值见 design §1.7；复杂交互可加大）
5. **使用 `capture` 抓取动态值**（账号 id、物品 id 等）

#### sleep 的合法用途（`rate_limit=0` 之后仍必须用 sleep 的场景）

`sleep` 等的从来不是限流（`rate_limit=0` 已关），而是**心跳驱动的游戏内计时**：
`start_busy(n)` 按心跳拍数计时（`start_busy(2)` ≈ 2 秒 busy），busy 期间命令被
`is_busy()` 拒（「你现在正忙着呢」）。所以：

- **唯一合法用途**：等 `start_busy` / 心跳脚本效果（吃药补血、打坐、经验果、
  尸体腐烂等跨拍生效的效果）走完。这类 sleep 的下限由 busy 时长/心跳拍数决定，
  症状是下一条命令被 `is_busy()` 拒——`wait` 等不到「忙完了」这种状态，只能等时间。
- **禁止**：`wait` 成功后再 `sleep`「缓冲」——`wait` 已完成同步，纯属白等；
  `cmd` 后直接 `sleep` 再 `menu`/`capture`——`menu`/`capture` 是 fail-fast 步骤，
  应改写为先 `wait menu`/`wait text` 兜住，而不是用 sleep 赌回包时机；
  `cmd`→`sleep`→`wait` 模式里的 sleep——`wait` 的轮询已覆盖，删掉即可。
- **`sleep` 不能代替 `wait`**：`wait` 是条件同步（等到为止），`sleep` 是盲等
  （睡够就走）。盲等要么早了（竞态）要么晚了（白费时长）。

### 9.2 修改现有剧本

- **修改服务端输出文本** → 必须同步更新剧本中的 `wait text`/`menu` 文本
- **修改交互流程**（增删菜单层级、改命令语法） → 必须同步更新剧本步骤
- **新增 lua-sample 功能** → 必须在对应剧本中添加覆盖步骤

### 9.3 禁止事项

- ❌ 在剧本中硬编码动态值（账号 id、物品 id、随机房间名）
- ❌ `filecopy`/`filedelete` 的目标写到 `test_tmp/`、`tmp/` 暂存区之外——教材（lua-sample）
  与生产（lua-default、src）目录一律拒绝（DSL 动词语义见 design §7）
- ❌ 省略 `wait` 直接 `cmd`（竞态导致不稳定）
- ❌ 使用 `sleep` 代替 `wait`；`wait` 成功后再加 `sleep`「缓冲」（见 9.1 的 sleep 纪律）
- ❌ 剧本之间有隐性依赖（除显式变量传递外）
- ❌ 在 `lua-sample` 目录下放测试脚手架（剧本、配置、脚本一律在 `tests/integration/`）
- ❌ 样本(lua-sample)是教材，不是测试夹具。禁止为了测试目的在sample中添加异常逻辑。禁止在未得到明确授权的情况下修改 sample 中的功能逻辑。
- ❌ 默认脚本（lua-default）目录是生产代码。禁止在未得到明确授权的情况下修改 default 中的功能逻辑。
- ❌ **为了测试目的而强行修改生产代码（C++ 引擎 `src/`、公共 Lua 库 `lua-default/`）**。
  遇到测试不通过，先在**测试侧**想办法（调整剧本、补给、起步资金、`-ResetDb`、用 config
  配置项等）；确需动生产代码时，必须**从设计/架构角度说明其合理性**（是真 bug 或真设计
  缺陷，而非「让测试通过」的补丁——例如硬编码几个键名去保值、在通用函数里塞测试特判），
  并配套单元测试。为图省事在生产代码里打「测试友好」补丁是禁止的。
- ❌ 断言只证明「命令发出去了」而不证明「结果对不对」（见下方 9.4）

### 9.4 并行下的断言纪律（新增/改动片段必过这三条）

1. **能用状态就别只看回执**：`attr` / `item` / `room` / `menu` / `object` 只与本人相关、最可靠。
   验「补上了没有」要断数值前后对比（`attr eff_hp >= 531`、`attr hp >= 405`），只断
   「你吃下一包金创药」证明不了血真的回来了；验装备要用 `wield 铁剑 右手`，只断 wield
   回执证明不了落在哪个槽位。
2. **文本断言要认得出「是我发的」**：`notify_fail`、`tell_object`、`say(msg, me)` 都私发、可直接断；
   `message_vision` 对本人渲染「你…」、对同房间旁人渲染「<名字>…」，所以取「你…」前缀才不会被
   别的账号串满足；改不动的房间/频道播报（尸体腐烂、排行榜）只能保证**只由本道触发**。
3. **稀缺资源唯一归属**：钉给唯一一道的稀缺资源（清单见 design §2.4）只能由该道采购
   与使用，并写进该道片段的头注释。

> `lua-sample/data/hooks.lua` 里的 `hooks.setup_human`（新角色起步本金）是**示例世界的正常
> 功能**：新角色靠它购物、置业、存款、自立门户。它不是测试脚手架，不是「为测试加的逻辑」，
> 删掉后多账号并行会因为全服只有一份山脚木箱金币而互相踩踏。

### 9.5 `/t` 目标是隐式状态（改片段时最容易踩）

- 目标由 `/t <ID>` 设定、`/t 0` 清除，**一直保持到下一条 `/t` 为止**；片段之间不会重置，
  被 `include` 串起来后更是跨片段生效。**`/t` 只收 ID**，不收显示名（ID 种类与作用域
  见 design §4，剧本侧用法见 §9.6⑥）。
- 命令对目标的要求各不相同，必须对上号：
  | 命令 | 需要的目标 | 目标不对时的回执 |
  |---|---|---|
  | `learn` / `talk` | **房间里的角色**（`get_room_char`） | `你要向谁请教？` |
  | `study` | **自己背包里的物件**（`get_self_object`） | `你要读什么？` |
  | `use` / `give` / `wield` / `sell` | **物品** | （静默失败或回错分支文案） |
  | `practice` / `enable` / `prepare` / `upgrade` / `sleep` / `exercise` | 不使用目标 | — |
- ⚠ 往已有片段**插入会改目标的步骤**时（例如「学高级剑法前先 `/t sample_sword_basic`
  + `/wield`」），必须在插入块的末尾把目标切回原对象，否则后续命令会拿到错目标。
  典型症状：`你要向谁请教？`、`你要读什么？`。
- ⚠ **高级技能 `valid_learn` 常带武器前置**（各技能的前置以教材脚本的 `valid_learn` 为准）。
  所以哪道要学哪条高级技能线，哪道就必须**自己买武器并在请教前装备**——
  木箱那把铁剑归 L1，别的道不能指望它。

### 9.6 互动断言纪律（L5/L6/L7 互动道新增/改动片段必过这七条）

多客户端互动让「别人发的命令产生我这边的输出」成为常态，断言纪律在 §9.4 之上加严：

1. **私发通道优先**：`tell` 私聊、菜单、`notify_fail`、`tell_object`、`say(msg, me)`
   都只发本人，可直接 `wait text` 断言；只有拿不到私发回执时才退回房间版文本。
2. **房间版断言必须含对方角色名**：`message_vision` 对旁人渲染「<名字>…」，而角色名
   带 runhex 每轮唯一，所以断「<对方名>…」形式（经 `$peer` 拼出）不会被别的账号串满足；
   仍然要避免断「全房间广播里出现某个通用词」这类谁都能满足的条件。
3. **会合房间避开其他道断言**：互动道会合/停留的房间应选其他道**断言不依赖**的房间
   （当前选山脚茶棚——仅 L1 装茶片段短暂经过且断言全为本人版）；若某片段要断房间
   播报，必须先确认该播报不会被并行道的路过账号干扰。
4. **超时信息写明「疑似对端未到位」**：配对道一侧 `wait`/`assert` 超时时，若失败点是
   会合（`wait object $peer`）或等待对方响应的步骤，排查先看**对端道**的日志（见 §10），
   不要只盯本道。
5. **稀缺资源归属**：互动道（L5/L6）不得采购/使用钉给唯一道的稀缺资源（清单见
   design §2.4）；互动双方要消耗的资源（如赠送的物品、摆摊的商品）由**互动道自己**
   的 provision 片段购买，声明写进道头注释。
6. **`/t <ID>` 只收 ID，不收显示名**（ID 种类、作用域与服务端/CLI 配套机制见 design §4）：
   - 剧本定向对方统一 `/t $peer_acct`（数字账号 ID，`run-integration-tests.ps1`
     注册后互注到各道 vars）；NPC/物品用对象英文 id（当前房间/背包内有效）；
   - `$peer`（角色名）仅用于**文本断言**（§9.6② 的含对方名渲染），
     一律不得作 `/t` 参数。
   同步手段：跨房间呼叫用 `/t $peer_acct` + `tell`；等待类步骤仍优先
   自触发（对方离房触发条件再回房）与宽 timeout 收敛的房间播报。
7. **`clear` 不得抹掉跨道信号**：`clear` 只用来清「本道自己命令的旧回执」，
    且不得落在「对方的广播/tell 可能已到达」与「消费它的 wait」之间——对端
    跑得比本道快时，跨道播报会先进本道缓冲，中途一条 `clear` 就把它抹掉，
    后面的 wait 干等超时且**播报永不重发**（教训案例见 design §2.4）。
    信号消费方要么该段全程不 clear，要么保证 wait 先于信号可能到达的时刻启动；
    发送方不知道对端进度，别把次序寄托在「对方应该还没那么快」上——**双向
    频道握手**是通用解（双方各先广播一句，收到对端的到站信号后再回话，两个
    到达都落在对端 wait 已启动的窗口内）：L8↔L3 的黑风寨错峰即此模式。

### 9.7 道文件（`lane_*.sce`）只放头注和 include

- `lane_*.sce` 只允许两类内容：**道职责头注**、**include**（顺序即执行序，顺序理由写在该行注释）。
- 其余一切内容都写成片段文件再 include 引入：命令、等待、菜单、清屏、采集、断言、延时、登录，以及收口步骤。
- **无例外**：任何 lane 都不许内联一行步骤。
- 提交前自检（硬门禁）：`lane_*.sce` 匹配 `^(cmd|wait|menu|clear|capture|assert|sleep|login)` 的行数必须为 **0**，非 0 先抽片段。

## 10. 常见故障与排查

| 症状 | 常见原因 | 排查步骤 |
|------|----------|----------|
| `wait text` 超时 | 服务端输出文本变更、编码问题、限流丢弃指令 | 1. 查服务端日志 `log/` 2. 确认 `rate_limit=0` 3. 对比实际输出与剧本期望文本 |
| `wait menu` 超时 | 菜单未弹出、菜单项文本变更 | 1. 手工复现 2. 检查 Lua 脚本 `do_talk`/`menu` 分支 |
| `login` 失败 | 数据库未就绪、账号冲突、密码错误 | 1. `-ResetDb` 重建库文件 2. 确认 `vars.txt` 变量正确 |
| 服务器启动超时 | PDB 加载慢、端口被占用、配置错误（上限参数见 design §1.7） | 1. `netstat -ano \| findstr <测试端口>`（port 见 `tests/integration/config.ini`）2. 检查 `config.ini` 路径 3. 手工起服看报错 |
| 覆盖率报告为空/异常 | 未加 `--optimized_build`、PDB 与 exe 不匹配、源码路径错 | 1. 确认同一次构建的 exe+pdb 2. `--sources src\*` 3. 重新构建 |
| CLI 连不上 | 端口错、host 错、服务器未就绪 | 1. 检查 `cli.conf` 2. 确认服务器日志有 `Listen on <测试端口>`（port 见 `tests/integration/config.ini`） |
| `你要向谁请教？` / `你要读什么？` | 改动片段时插入了会改目标的步骤、没把目标切回 | 1. 看失败行**之前最近的一条 `/t`** 2. 对照 9.5 的目标类型表核对 |
| `…必须手持剑类武器…学习高级…` | 高级技能 `valid_learn` 的武器前置没满足 | 1. 查该技能的 `valid_learn` 2. 确认本道 provision 有买、请教前有 `/wield` |
| `attr …` 超时 | 状态确实没到位，或改动后**没同步到客户端** | 1. 失败原因已附「（当前 名=值）」2. 拿当前值对比期望即可区分两种原因 |
| 配对道 `wait object $peer` 超时 | **疑似对端未到位**：对端登录失败/中途失败停摆，或本道自己先失败没走到会合 | 1. 先看对端道的日志（`test_tmp\e2e_lanes\lane<对端Id>.log`，**UTF-8 编码**——服务端 `tests\integration\log\` 才是 UTF-8、lane 日志经 CLI CP_UTF8 控制台层写入亦为 UTF-8；用 GBK/936 解码会得到伪可读乱码误导排查）2. 对端报告的 reason/失败行 3. 两边都正常再查会合房间名与 `$peer` 变量注入 |
| 观战道（L7）`wait text 比试开打/第二轮开打` 超时，或 L5 等 `比试观战完毕` 超时 | **疑似信号对端未到位**：L5 未发开战信号（比试/kill 段没跑到）或 L7 登录/移动停摆 | 1. 对端日志（L7 等信号看 `lane5.log`，L5 等回信号看 `lane7.log`）2. L7 是否已在山脚茶棚（`wait room` 行）3. `$spectator_acct`/`$peer_acct` 注入是否齐全（启动校验已拦一半未启用的情形） |
| 失败原因「服务器崩溃（未处理异常）」 | 服务器在关服路径（`WM_DESTROY`→等工作线程）崩溃；dump 由 `CCreateDump` 写出 | 1. 本轮新 dump **原地留在仓库根**（脚本会打印完整路径，不会挪走）；上一轮的旧 dump 已归档到仓库根 `crash_dumps\` 2. 用 `bin\jianghu.pdb` + WinDbg/cdb 分析 3. 崩溃发生在剧本判定之后，剧本本身可能是绿的，别只看剧本结果 |
| 失败原因「服务端日志出现未登记 ERROR/FATAL」 | 服务端侧报错（Lua 异常/命令失败/DB 错误），剧本只断言客户端收不到这些 | 1. 报告里看未登记签名与「本轮服务端日志」点名的 `M-D-e2e-<时间戳>.txt`（§4.5）2. 是预期（负测等）→ 按 §4.5 登记 `log-allowlist.txt` 3. 疑似真 bug → 先查根因再处置，不许直接拉黑（先例见 design §1.4） |
| L3 `wait text 黑风寨已清` 超时 | **疑似对端 L8 未到位**（L8 挂在战前准备/战斗、或握手反向 `wait L3已到寨口` 未获 L3 广播） | 1. 先看 `lane8.log`（§10 对端排查口径）2. L8 若停在 `wait text L3已到寨口` → 看 L3 的 corpse 段是否已广播「L3已到寨口」3. 反向：L8 广播被 L3 早到缓冲抹掉属握手设计已消除的情形——若复现检查两道 wait 段内是否被插入 clear |
| L8 `wait text L3已到寨口` 超时 | 对端 L3 未到寨口（L3 挂在 corpse 尸腐等待前的链、或 `wait 黑风寨已清` 已超时失败） | 1. 先看 `lane3.log` 2. L3 的失败会在报告里先暴露（两道互锁） |
| 耗时报告「超绝对预算」告警 | 剧本执行总耗时（注册+各道并行）超过 `-DurationBudgetSec` | 1. 看报告三行硬指标：关键路径道、吸收能力 2. Δ 归因点名新增场景 → 按拆分建议移道/新开道 3. 新增场景默认别进当轮关键路径道（design §2.5）4. 确需抬预算 → 改脚本默认值走 diff 评审 |
