# 任务搭建（quest-authoring）

## 0. 交付目标与输入

把一段故事梗概变成 **dataset** 上一条从接任务到发奖闭环的任务链：
玩家能领任务 → 按路线走到点 → 交谈/交付/战斗 → 拿到奖励，且通过
dataset 的完整验证。

**输入两项**：

1. **故事梗概**——六要素：关键 NPC、含糊的辅助 NPC、大体路线范围、
   情节（这四项**必给但可以模糊**，"塞外一带""有个老板娘"就够，
   清晰化是技能的事）；奖励规则、接取间隔（**可缺**，缺了用通用规则
   与"每岁一次"作拟议答案，且必进确认清单）。
2. **dataset 根目录**——用户给定的路径，是输入不是常量：用户给了
   就用哪个；没给就在确认清单里问（§1.3 第 1 项），不自行假设。

任务的**形状**（分段结构、消息长相、动词集合）已归纳固化在
`references/script-model.md`，动手前先读它——技能自带结论，
不依赖任何外部参考文件。

交付物 = **dataset 的改动**（修改既有文件 + 小量新增），外加一份阶段表
与改动清单。

## 1. 把梗概清晰化（模糊输入 → 定案）

梗概按六要素给全即可，**表述模糊是常态**，不必一次说清：
技能的职责就是清晰化——把每个模糊说法变成 dataset 里的具体落点，
总结成确认清单交用户定案。流程：

1. **解析梗概**，对照六要素（§1.1）抽取信息，标出模糊与缺口
   （"塞外一带""有个老板娘""奖励看着办"这类都算）。
2. **调研 dataset**（§1.2），把模糊说法翻译成具体候选：
   地名 → 真实房间序列，人名 → 具体 NPC 文件，情节 → 可落的交互与战斗。
3. **产出确认清单**（§1.3），逐项给出**拟议答案**让用户确认——
   拟议答案来自缺省规则（§1.1），但规则只是答案的来源，不是免问的借口。
4. 用户确认后，把清单结论固化进设计稿（Step 4）。

清晰化的边界：梗概没给的信息由技能调研补齐并给出拟议；
梗概给了但与 dataset 现状冲突的（如路线要经过不存在的房间），
以事实为底座提出改法，让用户改梗概或改路线——不擅自替用户改剧情。

### 1.1 要素与拟议答案的来源

梗概应当包含这六要素，缺失或模糊时按下表把它们清晰化：

| 要素 | 缺项/含糊时的拟议答案从哪来 |
|---|---|
| 关键 NPC | 调研 dataset 取实名与 id；撞名 → 拟议用绰号/别名区分 |
| 含糊的辅助 NPC | 三级裁定（§1.2.1），拟议答案是命中的那一档 |
| 路线范围 | 调研区域房间与门，拟议一条真实可达的房间序列 |
| 情节 | 切成阶段（`references/script-model.md` 的四条形状规则） |
| 奖励规则 | 缺省 → 通用规则 `references/reward-rules.md`（从既有任务完成点提炼），拟议给出 k 档位与理由 |
| 接取间隔 | 没提 → 拟议**每岁一次**（age 变化一个单位后可再接，即既有水位机制），并给出可选档（每天/每 X 分钟/一次性），进确认清单必问 |

### 1.2 调研 dataset

grep 入口与索引事实见 `references/dataset-api.md` §1：

- 关键/辅助 NPC：按中文名 grep `npc\`，拿文件路径、`set_name` 的中英文名、
  所在房间（反查哪个 room 摆了它）。
- 路线：列目标地区 `room\<区>\` 房间清单，读相邻房间的
  `add_object("door", ...)` 确认连通；机关房看
  `handle_action` / `valid_leave` / `do_look`。
- 物品：先找模板（`item\food\baozi.lua`、`item\food\mixian.lua`），
  再看有没有现成同名物。
- 状态：新键前缀 grep `"<前缀>/` 确认不撞既有链。

产出：**调研结论表**——每个要素的候选落点（复用哪个文件 / 新建哪个文件 /
改哪个房间），它是确认清单的事实底座。

#### 1.2.1 含糊辅助 NPC 的三级裁定

拟议答案按顺序停在第一个成立的档，并在清单里说明命中的理由：

1. **复用**：已有同名或同职能 NPC（店小二、庄主、掌柜…）→ 直接复用，
   情节贴到它的既有位置与性格上。
2. **改情节**：没有合适 NPC，但附近区域有别的可用 NPC → 改写这一处情节
   让位给它，比新增文件划算。
3. **新建**：剧情上确实不可替代才新建。小量添加预算：
   **NPC ≤ 3、房间 ≤ 3、物品优先模板改造**。超预算 → 把"梗概该收一收"
   作为问题提给用户，别自行扩编。

### 1.3 确认清单的形态

用提问工具（多问题一次提交）或一条编号清单呈现，每个待确认项三段式：
**问题 → 拟议答案 → 依据**。最小集合：

1. dataset 根目录（用户没给路径时）。
2. 每个关键 NPC 的落点（复用文件 / 新建文件）。
3. 每个含糊辅助 NPC 的裁定档位（复用 / 改情节 / 新建，超预算时必问）。
4. 路线的房间序列（跨区域或有机关时）。
5. 奖励：用户没给 → 拟议通用公式的 k 档位与理由；用户给了 → 复述确认。
6. 接取间隔：**即使没提也必问**——拟议"每岁一次"（age 变化一个单位后
   可再接），并列出可选档（每天 / 每 X 分钟 / 一次性）供改选。
7. 影响走向的其他分歧（结局分支、是否纳入门派日常等）。

**只问影响走向的事**：用户在梗概里已明确的、以及调研后唯一解的项，
不进清单。清单确认完才写代码——拿结论去对梗概比改十行代码便宜。

## 2. 工作流

| Step | 产出 |
|---|---|
| 1 解析梗概 | 要素清单 + 缺项/歧义标注 |
| 2 调研 dataset | 调研结论表（§1.2） |
| 3 确认清单 | 用户拍板后的定案（§1.3） |
| 4 剧情分段 | 阶段表（§4 模板） |
| 5 状态键与落位设计 | 键表 + 文件落位清单 |
| 6 编码落地 | dataset 改动 |
| 7 验证 | 三关全绿 |
| 8 交付说明 | 阶段表 + 改动清单 + 裁定理由 |

Step 1~5 合起来是**任务设计稿**；设计稿先于代码，对照梗概与路线自查过
再进 Step 6。歧义在 Step 3 已经问完，Step 6 期间不再打断用户。

### Step 4 剧情分段（按分段形状）

把情节切成阶段，一阶段一行填进阶段表。**段数不定**：简单任务几段，
复杂任务十几段、几十段，同类型段可以重复出现，分支与回环都允许——
形状的归纳与类型学见 `references/script-model.md`。这里是**四条形状规则**：

1. **一段一状态键**：每段对应一个状态值，进入该段 = 键取到该值。
   dataset 侧就是 `me:set("<链前缀>/<段名>", 1, "T")`；重复段用编号
   区分（`ab/talk1`、`ab/talk2`），不合并成一个键。
2. **推进必有唯一消息**：状态推进点必须发出一句**文本唯一、可匹配**的
   服务器消息（`self:say` / `tell_object` / `do_channel` / NPC 死亡 /
   得物提示）。任务的推进靠识别这句消息，
   消息不唯一 = 任务推进点不可识别。
3. **动词落在自动化集合内**：路线用连通的房间链表达，交互只用
   `ask` / `give` / `get` / `kill` / `use` / 房间动词（机关走
   `handle_action`）。复杂解谜（多步输入、自由文本）不要设计进来，
   没有动词能表达它。
4. **战斗要有回执**：击杀环节必须产出可识别的回执（NPC `die` 里
   发的得物/结算消息），交付环节必须产出得物消息——两者文本要能区分开。

### Step 5 状态键与文件落位设计

- 键名统一 `"<链前缀>/<语义>"`（如 `ab/talk`、`ab/fight`），
  前缀取任务名两字拼音或既有惯例，调研阶段已 grep 确认无撞车。
- 推进中的键放 `"T"` 临时袋（下线即失，任务中断在原地）；
  **完成标记与防重复水位放持久**（水位写 `me:set("<前缀>/jq", me:query("age"))`，
  接任务时用 `age` 比对判"本岁只能领一次"）。
- **接取间隔按确认清单的档位落位**：每岁 → 上面的 age 水位；
  每天/每 X 分钟 → 持久时间戳键 + 时间差判断；一次性 → 完成标记闸门。
  落位模板见 `reward-rules.md` §6。
- 放弃任务用 `me:del("<前缀>")` 清整棵子树（`del` 沿 `/` 递归到父映射）。
- 文件落位清单与调研结论表、确认清单三者对齐。

### Step 6 编码落地

按这个顺序写，每一步都能单独跑通校验：

1. **NPC 推进函数**：`create` 里注册 `set_inquiry_func`（回调，不是
   `set_inquiry`）与菜单；每段一个函数（`do_xxx` / `do_talk` /
   `accept_object` / `die` / `init`）。
2. **房间摆位与机关**：`add_object("npc", ...)` 放人、
   `add_object("door", ...)` 串路线、机关写 `handle_action` / `valid_leave`。
3. **物品**：优先 `load("item", "baozi")` 模板改造
   （`set_name` + `set("<任务标记>", 1)` + `set("owner1", me:id(1))`）。
4. **完成点奖励**：`references/reward-rules.md` 的通用公式内联在完成点。
5. **可选**：纳入门派日常 → `npc\class\zushi.lua` 加 `step` 分支。

硬规则与坑在 `references/dataset-api.md`，写码前通读其 §硬规则；
注释只写"这样设计为什么对"；测试计划、剧本、验收这类依据不进注释。

### Step 7 验证

在 **dataset 根目录**（Step 3 确认的那个路径）下依次过三关
（dataset 若自带验证规范文档，以其为准；没有就按下面三关跑）：

```powershell
# 1. 格式
Get-ChildItem -Path . -Recurse -Include *.lua | ForEach-Object { stylua $_.FullName }
# 2. 完整验证：stylua + --check-lua 全量 + 房间引用
.\validate.ps1
# 3. 房间引用（validate.ps1 已含，可单独复跑）
powershell -File .\_roomcheck.ps1
```

`--check-lua` 是**全量**校验，禁止抽样；`_roomcheck` 的
UNRESOLVED refs 与 duplicate name collisions 必须为 0。
用户给的是非标准 dataset 布局（缺 `validate.ps1`）→ 按其
`references/dataset-api.md` 的三关逐项手动跑，跑不了的项在交付说明里
写清缺什么。

### Step 8 交付说明

给用户一份短报告：阶段表、改动/新增文件清单、验证结果。
设计上的裁定（辅助 NPC 为什么复用这个、路线为什么绕这一段、
奖励取了哪个倍率、接取间隔取了哪档）要写进去——那是设计，不是流水账。

## 3. 硬规则速览

细节与出处在 `references/dataset-api.md`，这里只列最容易写错的：

- 回调用 `set_inquiry_func("话题", "函数名")`；`set_inquiry` 的第二参是
  **字面回答**，传函数名会让玩家看到函数名三个字。
- 脚本自定义函数不能 `self:do_xxx()` 调（`self` 是 C++ userdata，
  静默变 nil 后回退基类，菜单点了没反应）——同文件用 `local function`，
  跨文件传函数值。
- 菜单先 `add_menu_item(show, cmd, me)` 再 `send_menu(me)`；空菜单 = 无输出。
  菜单命令两种落点：裸关键词（回到 `do_talk`/ask）、`"$0动词 $1"`
  （进 `handle_action`，必须带 `$1` 才有目标）。
- 房间出口用 `add_object("door", ...)` 声明（签名与参数见
  `dataset-api.md` §7），引擎按 door 列表生成出口与寻路。
- NPC/房间 `base_name` = 文件名（去 `.lua`），room 的 `name` 全局唯一。
- Lua 里 `0` 为真：判状态一律 `~= 0` / `== 0`；`querystr` 判空用 `== ""`。
- `accept_object` 返回 1 且不 `destruct(ob)`，物品会落到 NPC 手上。
- 文件 UTF-8 无 BOM；Lua 侧标识符一律 `snake_case`
  （文件名 = 对象 `base_name`），常量 `UPPER_SNAKE`。

## 4. 阶段表模板

设计稿的核心就是这张表，一阶段一行；**行数不定**——下面五行只是
最小示例，重复段、分支段各占一行，段多段少都不影响它成立。

| 段 | 状态键 | 推进消息（唯一片段） | 路线（房间序列） | 交互 | 战斗/机关 | 回执与得物 |
|---|---|---|---|---|---|---|
| 1 接任务 | `xx/start=1` | NPC 说出任务台词的固定半句 | — | ask 关键 NPC | — | 置键 + 任务道具入包 |
| 2 赶路 | `xx/onroad` | 到达关键房间（`do_look` 提示） | A→B→C | — | 机关房动词 | — |
| 3 交涉 | `xx/talk` | NPC 的回答固定半句 | C | ask/give | — | 得物提示 |
| 4 战斗 | `xx/fight` | BOSS 死亡消息 | C | — | `kill` → `die` 判定 | 掉落 + 结算消息 |
| 5 交付领奖 | `xx/jq=age` | 完成播报 | C→D | give | — | 经验/声望/宝物 |

**迷你示例**（梗概："马贼围村，庄主托玩家退马贼，客栈老板娘通风报信，
路线在塞外一带，奖励没说"——各步的落点都以实际 grep 为准，示例只走流程）：

1. 确认清单拟议：关键 NPC"庄主" grep 无同名 → 拟新建（预算内）；
   含糊辅助 NPC"老板娘" → 该区域已有店小二类 NPC → 拟**复用**，
   把"通风报信"改贴成它的闲谈触发。
2. 路线拟议 → 列出目标区域 `room\<区>\` 房间清单，读 door 互指，
   拟一条真实可达的房间序列，机关房补 `handle_action`。
3. 奖励拟议 → 通用规则，按任务量级给 k 档位与理由
   （见 `reward-rules.md` §3）。
4. 战斗 → 马贼头目 `die` 判 `last_damage_from` + `owner` + 状态位，
   按 `dataset-api.md` §5 的战斗范式。
以上四条进确认清单，用户拍板后才落成阶段表。
