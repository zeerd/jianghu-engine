# 任务分段形状

> 本文件回答"任务要设计成什么样才玩得通"，不涉及 dataset 实现（见
> `dataset-api.md`）。结论从既有剧情任务中归纳提炼，技能自带，
> 不依赖任何外部文件。
>
> 任务的推进靠**文本消息**驱动（玩家与自动化都靠识别消息来判断
> "到哪一步了"），所以服务端的每一步都要外化成可识别的文本与可见对象——
> 这是贯穿本文件所有规则的根。

## 1. 分段骨架

整个任务由**一组状态键**驱动——常见是一条主线状态变量，外加若干
分支、计数、归属键；进入某阶段 = 主线状态取到对应值，而状态值的
每次变化都由一句唯一消息宣告：

```
状态：<任务名>
  段 1 接任务   进入消息：NPC 台词固定半句      → 置状态 + 任务道具入包
  段 2 赶路     进入消息：到达关键房间的提示    → 房间序列 + 机关动词
  段 3 交涉     进入消息：NPC 回答固定半句      → ask / give
  段 4 战斗     进入消息：BOSS 死亡 + 掉落结算   → kill → die 判定
  段 5 交付领奖 进入消息：完成播报（含数值）    → give → 发奖 + 水位
```

上面只画了五段——**段数不定**，十几段、几十段都常见；同类型段
可以反复出现（多轮交涉、多个击杀目标、多段赶路），复杂任务还会有
分支与回环。重复的段各自独立成行、各用各的状态键（`ab/talk1`、
`ab/talk2` 这类编号区分），不必强行合并。

段与段之间没有隐藏前置：玩家在任何一段重做该段的动作（重复 ask、
来回走、重复交付）都必须**幂等**——要么无害无输出，要么续上进度，
绝不重复发奖、绝不卡死。

## 2. 段的类型学

一阶段一行填进阶段表（SKILL.md §4）。下表是**归纳出的类型词汇，
不是固定流水线**：同一条任务里同一类型可以出现多次（两轮交涉、
三个击杀目标、四段赶路），段的排列也不必按表序，能分支、能回环。
每类段需要的落点与消息长相：

| 段类型 | 干什么 | 需要的落点 | 推进/回执消息的样子 |
|---|---|---|---|
| 接任务 | 问关键 NPC 领活 | `set_inquiry_func` + 菜单 | NPC 台词的固定半句 + 得物提示 |
| 赶路 | 走到目标房间 | 房间链 + 门；机关房动词 | 到达提示（`do_look` 给） |
| 交涉 | 问路、索要、谈判 | NPC 回调 + 菜单连问 | NPC 回答的固定半句 |
| 战斗 | 打赢指定目标 | `kill` → `die` 判定 + 状态位 | NPC 死亡 + 掉落 + 结算消息 |
| 交付 | 把任务物交给对方 | `accept_object` | 得物提示（"你给XX数量1的YY"式） |
| 机关/休整 | 开门、潜水、读书、休息 | 房间 `handle_action` / 动词 | 动词生效提示 / 状态恢复提示 |
| 交付领奖 | 终点结算 | 完成点 + 水位键 | 含任务名与确切数值的播报 |

**一段一条主线**说的是**单个段**：这一段要么赶路、要么交谈、要么
战斗，不混装；整条任务则不受此限——同一件事可以拆成多个段重复出现，
各段独立成行、独立状态键。

## 3. 从既有任务链反推出的形状事实

1. **远路用落点 + 收尾步行，近路整段步行**——服务端只需保证
   房间与门连通，不需要（也无法）感知玩家怎么赶路。
2. **回执都是短句且带专名**（"XX死了。""你得到数量1的YY。"）——
   这就是推进消息该有的样子：**专名 + 固定动词**。
3. **战斗有前置判定**：该不该打、打完算谁的，全靠状态位与归属标记；
   不靠"打赢了"这种事后标志。
4. **失败分支照写**：中途放弃要有清理路径（清状态子树），
   异常（被打断、重复触发）要能恢复。
5. **可变的中间目标**（打听中随机换人、多个杀手轮流来）是可表达的，
   但服务端**一次只发一个目标**更稳。

## 4. 自动化与识别对服务端设计的约束

任务要能被"文本匹配 + 固定动词"的自动化跑通，因此：

- **推进消息唯一**：全链无两句雷同；专名 + 固定动词，关键句里
  别堆积 `()[]{}.+?` 这类正则特殊字符。
- **状态外化**：自动化只能看到文本与可见对象，内部状态必须通过
  消息、得物提示、NPC 死亡等外化出来。
- **路线只保证连通**：房间/门串好即可；同名房间会造成寻路歧义，
  `_roomcheck.ps1` 查重名与断链。
- **动词落在固定集合**：`ask` / `give` / `get` / `kill` / `use` /
  房间动词（跳、潜、睡、读这类走 `handle_action`）。
  多步输入、自由文本的解谜不要设计进来——没有动词能表达它。
- **交付一次一件**：不要设计"同时给三件"的环节。
- **经验播报含"经验"字样与确切数值**，别只发一句叙事。
- **推进消息别写成易被过滤的样式**（谣言、通用表情那类）。
- **段状态用自定义键**，不依赖任何系统内部变量。

## 5. 自查（阶段表填完后过一遍）

- [ ] 每段的推进消息里都有**专名 + 固定动词**，全链无两句雷同。
- [ ] 单段只做一条主线，段与段靠状态键切换、无隐藏前置；重复段与
      分支段的键名彼此可区分（编号或语义不同）。
- [ ] 路线的房间链逐间有门，机关房写了 `handle_action`，无同名房间。
- [ ] 战斗环节有状态位门槛与明确回执，交付环节有得物回执。
- [ ] 所有交互动词都在 `ask/give/get/kill/use/房间动词` 集合内。
- [ ] 段内动作重复触发幂等（玩家来回走、重复 ask 不会卡死或重复发奖）。
