**一句话命题**：一个把「游戏」整体装进 Lua、C++ 只做时机申报的武侠 MUD 服务端引擎——
`src\lua\CombatRules.h:3-5` 的注释是整个概念的浓缩：「只申报引擎时机，规则内容与归属全归 Lua」。

[game-brief.md](../game-brief.md) 互补）。核心问题不是「这个引擎能开出什么世界」，

## 1. 引擎概念总览

**原始假设**：
一个中文武侠 MUD 的全部「游戏性」（战斗规则、任务、称号、经济、住宅）可以与
「引擎驱动」（网络、会话、调度、持久化）彻底分离——前者归 Lua 脚本，后者归 C++。
推论：内容作者不写一行 C++，仅凭 Lua 数据集即可交付一个完整可玩的世界。

**实现路径**：
- C++（~33k 行，`src\` 下 17 个模块）实现单进程服务器：IOCP 网络、1 秒心跳、
  对象体系（char/npc/item/room/condition 全部继承 `CContainer`）、战斗管线骨架、
  MySQL/SQLite 双后端持久化。
- Lua（引擎绑定面 ~280 个 `l_*` 函数，`src\lua\LuaBindDecls.h`）承载全部内容实例
  与其行为：每个房间、NPC、物品、技能、状态条件都是一个 Lua 脚本文件。
- 自带两套脚本根：`lua-default`（引擎兜底框架内容）与 `lua-sample`
  （自包含示例世界「青云山」，即开即玩，同时是内容编写的教材）。

**规模与复杂度**：
- 代码量：`src\` 约 33,000 行 C++；`lua-sample` + `lua-default` 约 8,000 行 Lua。
- 复杂度：**生产级**（非一次性原型）——有完整测试闭环
  （`run-coverage.ps1` Release 同构覆盖率门禁 + `run-integration-tests.ps1`
  CLI 无头剧本 E2E），协议有规范文档（`docs\protocol.md`），热重载与
  `--check-lua` 启动前校验齐备。

**结论**（已确认）：
- ✅ **成立**：C++/Lua 分界本身。Lua 覆写面（30+ hook）足以让内容作者改写
  战斗伤害、击杀奖励、购买定价、称号规则而不触碰 C++；双脚本根覆盖机制
  （同名脚本 `script_root` 优先、`default_script_root` 兜底）让「引擎自带框架、
  用户数据集盖章」成立。
- ⚠️ **需打磨**：编码契约（§4.1）、扩展命令机制有壳无货（§5.1）。
- ❌ **未成立**：见 §4 的具体裂缝——均为局部问题，不动摇分界本身。

## 2. 核心机制

**引擎做了什么（The Core Mechanic）**：
把每个可玩元素实现为「C++ 类骨架 + Lua 脚本实例」的双层对象，并在所有
规则决策点上留出 Lua 覆写钩子。C++ 在决策点调用
`CLuaHookCall`（`src\lua\LuaHook.h`）：**钩子缺席 = 静默放行，走 C++ 默认逻辑**；
钩子在场 = Lua 返回值直接改写结果。这就是「时机与规则」的分离：

| 引擎申报的时机（C++ 决定何时问） | 规则归属（Lua 决定答案是什么） |
|---|---|
| `attack_gate` — 现在能开打吗（`CombatRules.cpp:14`） | 哪些房间/对象拒绝战斗 |
| `calculate_damage` — 算伤害了（`Attack.cpp:427`） | 伤害数值与附加文案 |
| `kill_bonus` — 结算击杀奖励（`CReward.cpp:409`） | 击杀给多少经验（示例世界中山鸡给固定 10000） |
| `pre_buy` / `post_buy` — 买卖定价（`Vendor.cpp:149,192`） | 价格改写或否决 |
| `char_rule` — 属性上限（`CharRules.cpp:13`） | 如 `max_mp_limit`、`sleep_anywhere` |
| `pre_talk` / `pre_accept_object` — 对话/接收物品 | 任务状态机（引擎无 quest 类型） |

**核心循环**（内容作者/运营者的循环，引擎产品的真正用户）：
```
写/改 Lua 数据集脚本 → 热重载（5 秒扫描, HeartBeat.cpp:84）或 --check-lua 预校验
→ 起服实机验证（CLI 客户端 / 任意 TCP 客户端连 6600）
→ run-coverage.ps1 + run-integration-tests.ps1 质量闸门 → 角色/房间/住宅自动落库
```

**玩家侧幻想**（作为示例世界所呈现的产品面）：
「侠客行」类中文武侠 MUD 的文字江湖——拜师入门、读书练功、打坐回气、
下副本闯山寨、置办住宅、造谣上位。表现层完全交给文字与协议
（`&C=N&` 消息、`$RED` 色码、菜单 `SendMenu`/`AddMenuItem`）。

**涌现行为**（引擎没设计、但被 Lua 作者用通用钩子「发明」出来的）：
- **任务系统**：引擎根本没有 quest 类型。`lua-sample\data\quest.lua` 是唯一任务，
  纯靠 `hooks.pre_talk`（接单/复命）+ `hooks.pre_accept_object`（收货）+
  玩家 dbase 状态机（`quest/lilaotou` = 0/1/2/3）拼出「买药—送药—领赏 3000 经验」。
- **住宅经济**：引擎只提供「动态实例房」机制（`resolve_room_prefix` 按
  `house_<城>_<id>` 前缀惰性实例化，`lua-default\room\house_base.lua`）。
  715 行的 `resident_base.lua` 在其上装配出申请居民—选房—命名—缴费—
  仆人 NPC 防盗—托管代售—欠租 30 天充公的完整经济。
- **新手大厅的私有化**：注册大厅 `rk.lua` 声明 `type="fb"`（副本房），
  于是每个来访者拿到一份自己的房间实例，天然隔离并发注册流程。
- **概率内容**：老李头每 5 秒 1/10 概率在山顶刷「奇怪的树」宝箱
  （`sample_guide.lua` 的 `do_refresh` + `call_out`）——引擎无「随机事件」
  类型，这是 `call_out` + `random` 的自然涌现。

**玩家幻想如何被机制支撑**（示例世界给到的体验骨架）：
注册（天赋四维和必须恰好 = 84，`register_clerk.lua`）→ 山脚开箱得铁剑与
60000 文 → 问老李头拿 50000 经验见面礼 → 打山鸡（每杀固定 10000 经验）
→ 半山腰拜青云子（12 门技能全 500 的全才师父）→ 读书/练功/打坐成长
→ 山顶 menu「闯入山寨」下黑风寨副本（1 小时限时，BOSS 大当家会自疗）
→ 钱庄存贷 → 住宅区置业。

## 3. 成立的经验（What Worked）

### 机制层面

✅ **「钩子缺席 = 放行」的覆写契约**：C++ 默认逻辑永远可用，Lua 只在想改的地方
出现。**为什么成立**：内容作者不必理解引擎全部默认行为，增量式介入；
引擎升级不会因钩子签名变化而静默破坏脚本（没写钩子的世界照跑）。
**是否保留**：是，这是引擎产品化的护城河。

✅ **双脚本根覆盖**（`script_root` 优先 + `default_script_root` 兜底，
`GameInit.cpp:55`）：引擎自带框架（住宅、注册、监狱、PK 场、称号表），
用户数据集按同名覆盖。**为什么成立**：把「引擎该管的」和「世界该有的」
用文件系统而非 API 版本管理分开了。**保留**。

✅ **死亡是低成本的（软死亡策略，已确认为设计）**：死亡只掉经验
（`(combat_exp − sk_exp)/160`，`CReward.cpp:47-49`），`skill_death_penalty()`
是刻意的空实现（注释「当前策略为死亡不掉技能」，`CharLevel.cpp:161-162`），
且 `skill_death_recover()` 还会返还部分技能等级。**为什么成立**：
文字 MUD 的死亡惩罚若过重，社交与探索会被惩罚性焦虑压垮。

✅ **击晕归属与反抢怪（已确认为设计）**：击杀经验要求击晕者匹配
（`last_fainted_from`），带 60 秒归属窗口（`CharCombat.cpp:74`）、
同门击杀零经验（`CReward.cpp:234-237`）、队友/师父可分享归属。
**为什么成立**：多人同屏文字战斗里，抢怪是最容易撕裂社区的摩擦点。

✅ **PK 不产经验（已确认为设计）**：PK 击杀者经验收益恒为 0
（`CReward.cpp:337-340`），PK 的收益/代价走声望、罪恶（`kill/guilt`）、
城市卫兵（1.5 倍经验的 `pub_guard`）另一套账。**为什么成立**：
把 PK 的动机从「刷级手段」挪到「社会行为」，PK 场（`pk.lua`）内外
才可能是两种道德气候。

✅ **`give` 拒绝对玩家（已确认为设计）**：物品转移给玩家被硬拒绝
（「送人？你有何居心？」，`CmdStandardItem.cpp`），玩家间交易走
`listgoods`/`buy` 的摊位估值系统。**为什么成立**：堵死赠予洗钱/
RMT 走私，交易留痕可征税。

✅ **谣言频道 80% 匿名（已确认为设计）**：`random(10) < 8` 保匿名
（`ChatChannel.cpp:510-526`），配合 MP 消耗（rumor 花 20 MP 并减半当前 MP）
与限速禁言。**为什么成立**：确定性匿名造谣才有谣言生态，配合
`vote` 民主禁言形成自净闭环。

### 技术层面

✅ **万物皆容器**：room/char/item/corpse/副本全继承 `CContainer`，
重量/负重递归传播、`move` 自动卸装、dbase 以 `/` 路径寻址的两个
键值映射（`_M` 持久化 / `_T` 临时）承载一切状态。
**经验**：一套容器语义吃下了场景、角色、物品、尸体、副本五种需求。
**可复用**：是，这是新引擎设计的首选骨架。

✅ **菜单即命令**：菜单项就是命令串（`$0verb $1 <objid> $2 自由输入`，
`ContainerMisc.cpp:357-387`），客户端展开后代发。服务器不存任何 UI 会话状态。
**经验**：把 UI 归约为「服务器下发的命令建议」，协议与 CLI 客户端
零特判即可支持多级菜单。

✅ **延迟析构 + 心跳注册表**：`destruct()` 只标记，主循环下一迭代统一
`flush_destruct_list()`（`ServerSockWorker.cpp:210`）；心跳是
`object_id → CContainer*` 的 map，NPC 闲置即摘除心跳（`Char.cpp:183-186`）。
**经验**：单线程游戏循环里，「谁在 ticking」是一个显式可数的集合，
千人在线的空房间不烧 CPU。

✅ **`call_out` 调度器 + `call_out_combat`**：延迟回调挂在对象心跳上
（单位 = 1 秒心跳），`call_out_combat` 类型等战斗结束才触发。
**经验**：「战斗结束后做什么」在别的引擎要写状态机，这里是一个参数。

✅ **Release 同构测试门禁**：`run-coverage.ps1` 全程 Release|Win32
（生产同构），Debug 版测试内置 `TestConfigGate` 无条件报红
（`unit-test.instructions.md`）。**经验**：把「Debug 结果不作数」
做成硬门禁而非口头纪律，消除了「Debug 全绿但生产未验证」的假信心。

✅ **CLI 无头剧本 E2E**：`tests\integration\scenarios\*.sce` 用
`wait`/`assert`/`capture` 剧本驱动真实服务器 + 真实客户端，
多账号并行七条道，E2E 覆盖率与单测覆盖率互补、各司其职（口径与分工见
`docs\design\integration-test.md` §5）。**经验**：文字 MUD 的 E2E 天然
适合文本断言，剧本即回归文档。

## 4. 未成立的部分（What Didn't Work）

### 机制层面

⚠️ **GB18030/UTF-8 双编码契约** — ✅ **已修复（2026-10-24）**：脚本以 UTF-8
存盘、加载期统一转 GBK（`LuaEngine.cpp` `load_file_as_gbk`），Lua 字符串空间
即 GBK；但**房间**指令派发曾单方面把 `comm/arg/tar/dir` 转成 UTF-8
（`LuaRoom.inl`），与字面量反向，**NPC/Item** 分发则投递原始 GBK——差异一度
被写进教材注释（`monster_yongren.lua:363-365`）并被 ASCII 比较与脚本侧
`utf8_to_gbk` 回转掩盖。**修复**：三条分发路径统一原样压栈，
`house_base.lua`/`resident_base.lua` 的回转补偿（8 处）一并移除，教材与
`docs\handle_action.md`、架构文档同步改写；契约由
`tests/unit/test_dispatch_encoding.cpp` 钉住。**教训**：跨语言边界的编码
必须是单一契约，不能按调用路径各转各的——且「靠 ASCII 比较没出事」会让
反向契约存活很久。

❌ **野兽攻击脚本引用不存在的模块** — ✅ **已修复（2026-10-24）**：

## 5. 待打磨（What Needs Refinement）

⚠️ **Lua 命令扩展机制有壳无货**：`lua-default\command\README.md` 定义了
完整的 `command/<name>.lua` 惰性加载协议（返回 1 = 处理，-1 = 交还链），
但目录里**一个模块都没有**。**问题**：这是「命令玩法内容一律 Lua 化」
承诺的关键一环，目前只有 C++ 三张硬表在兑现。**路径**：把至少 2-3 个
低风险命令（如 `mudage`、表情类）迁到 `command/` 作样板。**工作量**：小。

⚠️ **`--check-lua` 的校验面** — ✅ **require 闭包已补（2026-10-24）**：
语法之外，字面量 require 现在解析到实体文件（§4 的 `skill_utils` 类事故
已被门禁拦下）。**仍缺**：`hooks.*` 名字白名单与 require 闭包之外的
运行期校验。**路径**：hook 名字白名单。**工作量**：中。

⚠️ **注释漂移**（§4）：三处已知 + 潜在更多。**路径**：修注释或删注释，
不做「注释翻译」——公式以代码为准写进文档（本文档即部分承担）。**工作量**：小。

⚠️ **`gain = 0` 的表达力**（`CReward.cpp:337-340`）：PK 零经验是**已确认的设计**，
但实现是「算完 gain 再无条件清零」——下一位读者必然当 bug 报。
**路径**：改写为显式早退 + 设计注释，让意图在代码里可读。**工作量**：极小。

⚠️ **单进程天花板**：`MAX_ONLINE_USERS 5000`、`login_limit 2500` 是编译期
常量与运行时配置，无跨进程/分线能力。**路径**：概念层面即接受（见 §8），
真要扩是架构级重构。**工作量**：大。

## 6. 关键认知（Key Learnings）

### 设计认知

💡 **「时机与规则」的分界线要画在决策点上，不是画在系统上**。
不是「战斗系统归 Lua」，而是「战斗管线的每一个骰子落点都可被 Lua 改写」。
**启示**：给引擎设计覆写面时，枚举决策点比枚举系统粒度更有效。

💡 **没有任务类型的任务系统是可行的，甚至是优点**。
`pre_talk` + dbase 状态机两个通用钩子足以表达任意任务，
而引擎不必背上任务链、目标类型、奖励模板的复杂度。
**启示**：内容 DSL 优先组合通用钩子，谨慎新增专用类型。

💡 **文字 MUD 的「数值策划」活在 hook 里而非表里**。
山鸡固定 10000 经验、老李头 50000 见面礼、经验果 +100000——示例世界的
数值全是教学占位（已确认），目的是让机制「看得见」，不是节奏基准。
**启示**：教材数据集的数值不该被反向当作设计意图；新世界必须自带
自己的经济表（`level_exp.lua` 已经是可替换的表驱动，这是对的）。

### 技术认知

💡 **惰性单例房间表（`g_room_list`）+ 前缀实例化**：房间按 `base_name`
全局惰性创建，住宅用 `house_` 前缀在同一机制上长出动态实例。
**启示**：一个「按名取物」的对象表，静态世界与动态实例不用两套系统。

💡 **战斗是房间不是状态**：`CFightRoom` 是按需 `load_item("fight_room")`
创建的虚拟房间，双方被搬进去才开打；组队、观战（`guard`）、
逃跑（50 AP）都是容器操作。**启示**：把战斗域建模为空间而非角色 flag，
多人混战的归属、规则、观战自然落在容器语义里。

💡 **经验衰减而非经验封顶**：玩家 `combat_exp > 10000` 后只有一半有效
（`6000 + exp/2`，`CombatCalc.cpp:33-34`），玩家战力公式里的经验项被
刻意打折——这是**沿袭经典 MUD 的遗产约定**（作者确认按 legacy 记录，
非本仓库的刻意设计），但其效果值得注意：它把「等级/技能深度」
置于「刷经验量」之上。**启示**：遗产机制也值得在概念层面重述效果，
即使不宣称它出于设计。

## 10. 技术备注

**实现概况**：
- 语言/运行时：C++（Win32，MSVC，/MT）+ Lua 5.5（`3rd/lua55`）；MySQL/SQLite 双后端。
- 架构：单进程；IOCP 网络线程 + 单游戏主循环（1 秒心跳，`ServerSockWorker.cpp:224-246`）；
  延迟析构队列；对象心跳注册表。详见 `docs\architecture\engine-core-architecture.md`。
- 对象体系：`CMainObject`（dbase `_M`/`_T`）→ `CContainer`（重量/子对象/调度）
  → `CChar`/`CItem`/`CRoom`…；Lua 侧以 `CLuaXxxT<T>` 模板包装，脚本 `type` 字段选基类。
- 战斗管线：12 阶段（`Attack.cpp:25-66`），队伍轮换制虚拟战斗房间（`FightRoom.cpp`），
  战力公式 `(level³/3 + combat_exp)/30 × abi`（`CombatCalc.cpp:14-58`）。
- 进度：等级上限 176（`level_exp.lua` 表 + 分段近似回退），技能上限
  `level2skill` 分段线性（`CharLevel.cpp:29-49`），师徒/夫妻教学的
  `sk_exp` 独立经验预算。

**取过的捷径**（引擎自身）：
- 编码：房间/NPC 两条派发路径各自转码（§4.1）。
- 授权：巫师命令授权表与 handler 表分置（§4 死代码）。
- 注释：多处用注释记录意图而未随代码更新（§4）。

**技术债**（若继续产品化）：
- 编码边界统一（最高优先）
- `--check-lua` 闭包校验
- 死代码与接线一致性
- x64 移植（README 明示暂停）

## 13. 开放问题

**设计问题**：
1. **支柱是否成文**：§8 六支柱系反推。哪些是自觉纲领、哪些是巧合的一致？

   `CombatCalc.cpp` 的半衰阈值是唯一调节旋钮——它该不该进 Lua `char_rule`？
4. **`command/` 目录的战略**：命令 Lua 化是承诺（README 分工章节），
   但零实现。是迁移，还是收缩承诺、删掉协议？

**技术问题**：
5. **x64 何时要**：README 明示暂停。触发条件是什么（内存压力？
   依赖升级？）——目前无成文判据。
6. **编码统一的破坏半径**：若在 C++ 边界统一转码，存量数据集里
   「依赖现状」的脚本（如 `monster_yongren.lua` 的 GBK 假设）会破多少？

7. **容量的真实上限**：5000 在线是编译期常量而非实测结论。
   单机在何种房间/战斗密度下先撑不住（内存？心跳耗时？DB 写放大？）——无基准数据。
8. **`--check-lua` 能走多远**：require 闭包校验可做；hook 签名校验
   （参数个数/返回值形状）Lua 侧无静态类型，能查到什么程度？
