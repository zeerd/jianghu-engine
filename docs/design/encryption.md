# 通讯密钥与口令存储（加密策略）

本文记录两项安全机制的**设计**：通讯帧 XOR 密钥的可配置化、账号口令的加盐哈希存储。
怎么做（配置项名、列名、命令）以代码与 `data/config.ini` 为准，此处只写为什么这样设计、
边界在哪里。计划书见 `docs/plans/encryption-strategy-update.md`。

---

## 1. 通讯帧密钥

### 1.1 现状与问题

帧编解码是**自逆 XOR**：`src/util/StringUtil.cpp` 的 `decode_str` 收发两侧共用，
CLI 侧 `cli/src/protocol.cc` 的 `encode_str` 是同一变换。历史实现把密钥写死在两处
源码里（服务端 `"\15L\26A\18N\12W\25O\33O\6D"`、CLI 同值），改一次密钥要改两处源码
并重编两侧，实际上等于不可改。

XOR 只是混淆不是加密，密钥可配置化也不改变这一点——它的价值是**把密钥从代码里
挪进部署配置**，让「换密钥」成为运维动作而不是代码变更。

### 1.2 密钥来源与回退

- 服务端：`decode_str` 每次取 `[security] comm_key`，空或缺省回退内置默认密钥。
- CLI：`Config.comm_key`（`cli.conf` 的 `comm_key`）由 `ClientCore` 构造时下发给
  `protocol::set_comm_key`，空串同样回退内置默认。
- 内置默认值即历史硬编码值，**因此不配置就与旧版本完全互通**（旧客户端不升级也能连）。

设计取舍：

- **配置值原样作为密钥字节**，不做十六进制/转义解析。内置默认密钥含控制字节
  （`\15` 是 0x0D、`\18` 实为 0x01+'8'），这类值写不进 INI，但它由回退分支承载；
  运维自定义的密钥用可打印 ASCII 即可，省掉一套转义语法与其歧义（八进制几位、
  转义不完整怎么办）。
- **空值一律回退默认**：密钥长度为 0 会让游标恒停在 `key[0]` 上越界读，空密钥
  不是「更弱的密钥」而是未定义行为，必须在入口拦掉。
- 服务端不做缓存，每次从 `g_ini_data` 取：配置在启动时已加载，运行期不会变，
  每帧两次 map 查找相对网络 I/O 可忽略，换来的是没有初始化时序问题
  （任何时刻调用 `decode_str` 拿到的都是当前生效密钥）。
- 两侧必须同值。E2E 的 `tests/integration/config.ini` 与 `cli.conf` 配同一把非默认
  密钥，服务端或 CLI 任一侧读不到配置都会在登录帧上立刻暴露。

### 1.3 已知边界

- `tools/wireshark-ccjh.lua` 里还有第三份硬编码密钥（抓包解码用）。部署改了
  `comm_key` 后该工具需手工同步，否则解出来是乱码——它是调试工具，不参与运行时。
- 密钥只在配置文件里明文存放，与 `config.ini` 里数据库口令同等敏感，属既有形态。

## 2. 口令存储

### 2.1 现状与问题

`jianghudb.cc_passwd` 直接存明文（写入侧只剥单引号），`cc_verifypass` 在 SQLite 存
明文、在 MySQL 存 `OLD_PASSWORD()` 弱哈希。数据库一旦泄露，所有口令直接暴露。

### 2.2 存储形态

新写入一律：**16 字节随机盐 + PBKDF2-HMAC-SHA256（100k 迭代）派生 32 字节**，
两者 Base64 后分别落 `*_salt` / `*_hash` 列；明文列 `cc_passwd` / `cc_verifypass`
写入即清空。

- 原语集中在 `src/util/Crypto.h`（Windows CNG：`BCryptGenRandom` 取盐、
  `BCryptDeriveKeyPBKDF2` 派生；PRF 句柄必须带 `BCRYPT_ALG_HANDLE_HMAC_FLAG`，
  否则 CNG 返回 `STATUS_INVALID_PARAMETER`）。凭据写入统一走
  `make_password_credential`，注册/改密/巫师自举/明文迁移共用一条路径。
- Base64 字符集不含引号与反斜杠，落库字面量无需转义，也天然过得了 SQL 注入面。
- 100k 迭代在单核上约几十毫秒：登录一帧、`/password`、`/validate` 各一到两次，
  同步计算可接受。若将来要在每条命令上做口令核对，再谈调低迭代或异步化。

### 2.3 列与迁移

新增四列：`cc_passwd_salt`、`cc_passwd_hash`、`cc_verifypass_salt`、
`cc_verifypass_hash`。

- **一律追加在建表列清单末尾**。`verify_user` 取 `select *` 后按**位置**读建档字段
  （`row[17]` 是存档、`row[4..7]` 是四维、`row[20]` 是权限），把新列插在中间会让
  这些下标整体错位；SQLite 与 MySQL 的 `ADD COLUMN` 也都追加在表尾，与首建一致。
- `CREATE TABLE IF NOT EXISTS` 不给已有表补列，所以 `prepare_tables` 末尾做一次
  **列存在性探测**（SQLite `PRAGMA table_info` / MySQL `information_schema`），
  缺哪列补哪列。不采用「直接 ALTER 再忽略报错」：两种方言都只能靠错误文案区分
  「列已存在」与真失败，而错误文案不可依赖。
- 探测查询失败即**开机失败**：缺列时注册与登录会在运行期逐条报错，不如在启动
  阶段一次性暴露。探测有结论但列缺失，同样在启动期补完。

### 2.4 迁移策略：读时迁移

旧数据没有哈希列的值，处理方式是**校验通过后原地迁移**（写入盐与哈希、清空明文列）：

- 登录 `db_authenticate_account` 与暗码 `db_verify_password` 都走「哈希优先、
  旧行等值比对、通过即迁移」。写路径（注册/改密/暗码修改）则从一开始就是新形态。
- 迁移写失败**只记日志、不改变本次校验结论**——口令本身已验证通过，把登录失败
  归因于一次后台升级是本末倒置，下次登录还会再试。
- 迁移是单向的：**降级到旧版本二进制将无法登录已迁移账号**（旧代码只比对
  `cc_passwd`，而它已被清空）。降级需要同时回滚数据库备份，这是接受的代价。

### 2.5 明文列为空必须拒绝

明文列迁移后恒为空串。若「哈希列为空」时仍按 `cc_passwd == 输入` 等值比对，
**空口令就能顶替任何已迁移账号的真口令**（登录帧里密码字段为空是可达的）。

因此主密码的凭据存在性是硬条件：哈希列非空走哈希；哈希列为空但明文列非空才走
等值比对；两列皆空视为「没有凭据」，一律拒绝，无论输入是什么。

暗码不适用这条：未设置暗码的账号两列皆空，而「空入参 + 未设置 = 通过」是被依赖的
既有语义（新号首次设暗码前的口令确认走这条），所以暗码保留 SQL 侧等值比对的原语义。

### 2.6 两套规范化契约

| 凭据 | 写入/校验前的规范化 | 出处 |
|---|---|---|
| 主密码 `cc_passwd` | **剥除**单引号 | 登录口 `replace_string` 对整条登录串剥引号 |
| 暗码 `cc_verifypass` | 单引号**替换为空格** | `LoginAuth::verify_password/change_verify_password` |

两套契约都保持原样，哈希作用在**规范化之后**的字节上——作用在之前会让「登录侧
规范化过的输入」永远对不上存储值（自我锁死）。规范化在读写两侧各做一次、幂等。

### 2.7 日志

认证失败统一记 `database fail: user:<id> passwd:<口令> store null`（账号不存在与
口令不符同形：库里查不到与该口令匹配的凭据）。DB 查询失败、派生失败、迁移失败
各有独立日志，不与认证失败混淆。

保留「失败尝试的口令进日志」是既有行为：它是认证失败唯一可锚定的变量部分。
改这一行需要同步 `tests/integration/log-allowlist.txt` 的签名。

## 3. 尚未做（有意留待）

- **AES-GCM / 会话密钥协商**：当前 XOR 仍是混淆。引入 ECDH + AES-GCM 要改协议帧
  结构与握手，超出本次范围。
- **Argon2id**：抗 GPU 破解更强，但要引第三方库；当前威胁模型下 PBKDF2-100k 够用。
- **密钥轮换**：`comm_key` 多版本（按版本号解码）未做；换密钥目前等价于停服改配置。
