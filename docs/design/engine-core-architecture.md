## Context

**Problem Statement**:

`jianghu-engine` 是一个 Win32 文字 MUD 服务端。它必须同时满足四件事：

1. 大量 TCP 连接的异步 I/O；
2. 一个**共享可变**的世界状态（房间 / NPC / 物品 / 玩家），且所有连接都能改它；
3. 可热更、无需重编译的外置内容与规则；
4. 跨 MySQL / SQLite 的持久化。

核心矛盾是第 1 与第 2 条的冲突：I/O 天然要并发，世界状态天然是共享可变的，
而**并发访问共享可变状态是这套系统最主要的故障源**。整个架构都是围绕这一矛盾展开的取舍。

**Background**（inferred from code）:

- 平台是 Win32 / Winsock，IOCP 是该平台原生的高并发 I/O 模型；构建固定为 `Release|Win32`
  （生产与覆盖率均为 32 位，见 `run-coverage.ps1`、`unit-test.instructions.md`）。
- 内容（房间 / NPC / 物品 / 技能 / 任务）的变更频率远高于引擎本身的变更频率，
  内容必须外置，否则每次调数值都要重发布。
- 世界规模小而状态复杂：单进程、单房间数以百计、在线玩家以千计的量级，
  这一规模下"正确性优先于吞吐"是划算的。
- 替代方案（多线程模拟、异步 DB、组件化对象模型）在技术上都可行，代价各不相同。

**System Scope**:

影响 `src/` 全部 17 个子系统（约 35k LOC / 232 文件）：
`net`、`object`、`engine`、`char`、`npc`、`item`、`room`、`cmd`、`combat`、
`lua`、`db`、`skill`、`user`、`config`、`util`、`interfaces`，以及入口 `main.cpp`。

**不在此范围内**：`cli/`（命令行客户端，独立工程与独立测试）、`tests/`（验证手段，不是被决策的实现）、
`lua-default/` 与 `lua-sample/`（内容，受本决策约束而非本决策的一部分）。

**Stakeholders**:

- **引擎维护者**（`src/`）：需要知道哪些代码可以假设"没人和我抢锁"。
- **脚本作者**（`lua-default/`、`lua-sample/`）：需要知道什么逻辑该放 Lua、什么不该放，
  以及 C++ 回落（`base_*`）与 `hooks.*` 的边界。
- **运维 / 部署**：`data/config.ini`、数据库选型、启停流程（`WM_CLOSE` 优雅关服）。

## Decision

**Approach Taken**（as implemented）:

> **IOCP 只搬包，单线程跑世界，Lua 拥有内容。**

三层分工，各层之间只通过**线程安全队列**和**虚函数 + 脚本回落**两种边界通信。

### 1. 网络层：IOCP proactor，只做 I/O 与分帧

- 线程构成（启动时全部创建，此后不变）：

  | 线程 | 数量 | 职责 |
  |---|---|---|
  | UI / `WinMain` 线程 | 1 | 隐藏窗口 + `GetMessage` 循环；`WM_TIMER`(1s) 仅轮询 `g_reboot`（`src/main.cpp:118-130,157,161-168`） |
  | IOCP worker（`server_worker_thread`） | N = CPU 数 | `GetQueuedCompletionStatus` + 收发完成处理（`src/net/ServerSockWorker.cpp:32-130`，创建于 `src/net/ServerSockHandler.cpp:168-209`） |
  | 游戏线程（`main_worker_thread`） | 1 | **整个游戏模拟 + 全部 DB I/O**（`src/net/ServerSockWorker.cpp:224-246`，由 `WM_CREATE` 启动，`src/main.cpp:150`） |

- 一个完成端口 `g_iocp`；监听 socket 以 `IOCP_ACCEPT_KEY` 为 completion key，
  每个已接受 socket 直接以 `CGateInfo*` 为 completion key（`src/net/ServerSockHandler.cpp:133,234-235`）；
  预投 4 个 `AcceptEx` 并在完成时补投（`ServerSockHandler.h:39`、`ServerSockHandler.cpp:138-140,263`）。
- 收包路径：worker 完成 → `dispatch_gate_recv` 分帧成 `_TRECVBUFF`
  （`RECV_MSG_LOGIN` / `RECV_MSG_COMMAND` / `RECV_MSG_EXIT`）→ 推入该连接的
  互斥队列 `CGateInfo::m_recv_buff_q`（`src/net/GateRecvDispatch.cpp:11-72`）。
- 发包路径：`CUser::send_command` → `send_off` → `send_to_client` → `CGateInfo::send`
  入队 → `try_send_next` 用 `InterlockedCompareExchange(&m_do_sending,1,0)` 保证
  **每连接同时只有一个未完成 WSASend**（`src/net/GateInfo.cpp:54`），天然保序。
- IOCP 线程**只触碰 socket 与队列，不触碰任何世界状态。**

### 2. 模拟层：唯一游戏线程，串行执行，世界状态免锁

`main_worker_thread` 主循环（`ServerSockWorker.cpp:224-246`）依次：

1. `process_user_message()` 遍历所有 gate、出队分发：
   `RECV_MSG_LOGIN` → `on_login`；`RECV_MSG_COMMAND` → `splite_command_parse` → `CUser::push_command`；
   `RECV_MSG_EXIT` → `on_offline` + 调度删除（`ServerSockWorker.cpp:134-222`）。
2. `user_command_loop()` 逐条执行玩家命令（`src/user/UserMgr.cpp:89-101` → `CUser::handle_command`）。
3. 每 1000 ms 调 `call_heart_beat()`：刷新 `g_current_time`、Lua 热更检查（每 5 s）、
   遍历 `g_heart_beat` 调 `obj->heart_beat()`、`look_for_objects_to_swap()`（房间重置，900 s）
   （`src/engine/HeartBeat.cpp:77-107`）。
4. `flush_destruct_list()` 真正 `delete` 本轮标记的对象。

**全部数据库 I/O（登录校验、读档、写档、自动存档、关服批量存档）都发生在这条线程上。**
没有异步 DB、没有写队列、没有批处理、没有事务（`src/` 内无任何 `BEGIN`/`COMMIT`）。

### 3. 内容层：C++ 拥有引擎与热路径，Lua 拥有内容与规则

- `CLuaEngine` 单例、单 `lua_State`、`luaL_openlibs` **无沙箱**（`src/lua/LuaEngine.cpp:144-151`）。
- 脚本磁盘上是 UTF-8，**加载期统一转 GBK**（替换 `package.searchers[2]` 的 GBK searcher，
  `LuaEngine.cpp:80-134`），使 Lua 字符串与 C++ 字符串无需逐次转换即可比较。
- **每 `base_name` 一个脚本**（文件名即数据键），脚本必须返回 table；按
  `"type_dir/bareName"` 复合键缓存于 `LUA_REGISTRYINDEX`，默认根脚本可被用户根同名覆盖
  （`LuaEngine.cpp:656-758`、`scan_script_tree` `353-397`）。
- **对象 → 脚本的接线**：工厂 `create_npc/create_item/create_room/create_fb`
  （`src/engine/SetupObjects.cpp:63-274`）在脚本存在时实例化 `CLuaNpcT<T>` / `CLuaItemT<T>` /
  `CLuaRoomT<T>` / `CLuaSkill` 模板包装，否则走纯 C++ + DB 装载。
  包装类**重写虚函数** → `lua_rawgeti` 取脚本表 → `lua_getfield` 取方法 → `lua_pcall`；
  函数缺失则**回落 C++ 基类实现**（典型形态见 `src/lua/LuaNpc.inl:233-267`）。
- **Lua → C++ 回落**：`self:base_create()/base_handle_action()/base_do_talk()/…`
  是 `l_base_*` 绑定（`src/lua/LuaBindGlue.cpp:287-660`），刻意调用**非虚**基类方法，
  以打断 C↔Lua 无限递归。
- **全局扩展点**：`hooks.*` 表共 25 处调用点（`fight`、`attack_ratios`、`calculate_damage`、
  `pre_talk`、`pre_buy`、`char_rule`、`rank_rule`、`object_create` 等）；
  `hooks` 不存在是**合法状态**（`src/lua/LuaHook.h:5-6`）。
- **热更**：心跳每 5 s `check_for_reload()`（mtime 快筛 + 哈希确认），
  通知存活实例刷新 `m_script_ref` 并调 Lua `reload(self)`；
  `reload_script` 先装新版本，**失败则保留旧 ref**（`LuaEngine.cpp:783-878,936-981`）。
- **分工铁律**：引擎不知道"任务"这种类型；法术一律 Lua（`CSkill::Magic_t.lua_func`）；
  但战斗主循环、命令框架、移动、网络、持久化、心跳调度在 C++。

**Key Implementation Details**:

- **命令分派链**（`src/cmd/CmdHandle.cpp:152-317`）：
  限流（5 秒 15 条，第 4 次违规 `disable_player`，`CmdHandle.cpp:184-216`）
  → 环境拦截 `dynamic_cast<IActionHandler*>(where)->handle_action(...)`
  → 目标对象拦截（存活目标先过 Lua `combat_rule_reason("command_gate")`）
  → 频道 `g_channel.do_channel`
  → `handlecommand` 依次查 `g_cmd_standard` / `g_cmd_user` / `g_cmd_wizard` 三张
  `std::map<std::string, fn>` → **Lua 回落 `lua_call_command`**（`CmdHandle.cpp:314`）。
  前缀 `"0 "` 的命令绕过队列立即执行（`src/user/User.cpp:398-401`）；命令队列上限 20。
- **对象模型（有意设计）**：`CMainObject`（`src/object/CObject.h:15`）→ `CContainer`
  （`src/object/Container.h:25`）→ `CChar` / `CItem` / `CRoom` / `CDoor` / `CSkill` / `CCondition`。
  全部状态是**两个字符串键属性袋**：`_M`（持久 dbase）与 `_T`（临时 dbase），
  键为斜杠路径（`"family/master_id"`、`"fight/is_fighting"`）；类型判定走整数属性枚举
  `IS_ITEM/IS_NPC/IS_ROOM/IS_USER/...` + `query_attr(int)`，**不依赖 RTTI**
  （`CObject.h:200-254`）。`CChar` 与 `CItem` 各实现 5 个 mixin 接口，
  `CRoom` 实现其中 3 个（无 `IHittable`/`IEquippable`）。
- **注册与生命周期**：7 张全局注册表（`g_room_list` / `g_npc_list` / `g_item_list` /
  `g_user_list` / `g_skill_list` / `g_condition_list` / `g_vendor_list`，`src/object/Global.h:142-148`）；
  对象 id 来自单调计数器 `g_object_id`（`src/object/Container.cpp:20,39`）。
  `destruct()` 只标记 + 摘注册表 + 推入 `g_destruct_list`，
  真正 `delete` 由心跳 `flush_destruct_list()` 执行（`src/engine/GameObject.cpp:127-161`、
  `HeartBeat.cpp:29-42`），因此回调后检查 `g_last_destruct_object == object_id()` 成为全库惯例。
  容器内 `m_item_list` 是**非拥有裸指针**，`CContainer::move` 负责搬运（`src/object/ContainerMove.cpp:22`）。
- **线程间共享**：仅 4 处锁 —— 每连接队列的 `std::mutex`（`src/object/Queue.h:15-65`）、
  `CGateInfo::m_cs`（`std::recursive_mutex`，`src/net/GameSvr.h:102`）、
  `g_gate_list_mutex`、`g_destruct_list_mutex`；`CGateInfo` 用 `Interlocked` 引用计数。
  **世界状态本身没有任何锁。**
- **连接生命周期**：`CGateInfo::m_login` 状态机
  `GATE_LOGIN_{NOT_LOGGED_IN,LOGGING_IN,NORMAL,CLOSING(-1),PENDING_DELETE,SCHEDULED_DELETE}`
  （`src/net/GameSvr.h:37-42`）；**新连接的第一包被整体视为登录包**
  （`GateRecvDispatch.cpp:26-41`），`LOGGING_IN` 期间丢弃其余流量。
- **协议**：`\t` 分帧（缓冲 ≥1024 无终止符则强制吐包，`src/net/GateInfo.cpp:131-156`）；
  载荷是 `&C=<code>&M=<text>&` 形式的键值对（`src/util/StringUtil.cpp:35-60`）；
  全链路 GBK；**混淆（非加密）**：固定 9 字节密钥 XOR（`StringUtil.cpp:77-97`），无压缩无加密。
- **持久化**：`IDatabase* g_db` 单一全局连接（`src/db/IDatabase.h:103`，定义 `Sql.cpp:18`），
  启动时 `init_sql_server` 打开、关服关闭、**无重连**。
  对象走"整行 JSON blob"（`CMapping::get_buffer()` 写 `t_item/t_npc/t_room/t_box` 的 `obj_data`，
  `src/object/ContainerMisc.cpp:148-232`）；玩家走手写
  `UPDATE jianghudb set cc_name=..., cc_savedata='<JSON>'`（`src/char/CharSave.cpp:93-141`）。
  Schema 管理 = `CREATE TABLE IF NOT EXISTS`（`src/db/DbTables.cpp:95-245`），**无版本表、无迁移**。
  脚本可用 `save_table`/`save_key` 自选路由表，C++ 不认识具体表名。
- **配置**：`--config <path>` 覆盖默认 `data/config.ini`（`src/util/CommandLine.cpp:10-58`，
  `main.cpp:61`）；`ini_load`/`ini_get` 读进全局 `g_ini_data`；
  各模块在 `init_game` 时**快照**成静态成员（`src/config/ServerConfig.cpp:13-21` 等），
  运行期改配置需重启（Lua 侧的 `ini_get` 绑定是实时的）。

**Clarified Rationale**（from user，非推断）:

- **单线程是有意选择**：目的是**简单性与正确性** —— 世界状态免锁，
  从根上消灭"漏加锁"这一类缺陷。当前规模下游戏线程上的阻塞 DB 是**被接受的已知代价**。
- **属性袋 + 整数属性枚举 + 5 个 mixin 接口是有意设计**：字符串 dbase 数据驱动、
  对脚本友好、序列化廉价（整袋即 JSON）；接口是**有意的局部拆解**方向，不是待清理的遗留。
- **C++/Lua 分工是既定长期契约**：C++ = 引擎核心与热路径，Lua = 内容与规则。
  本 ADR 的作用之一就是把这条原本只存在于人脑中的契约写下来。

## Alternatives Considered

*（以下为推断或经问答澄清；标注 `INTENT UNKNOWN` 者未获作者确认。）*

### Alternative 1: 多线程模拟（分片锁 / 无锁结构）

**Description**: 按房间或区域分片，多个模拟线程并行推进世界；或采用无锁数据结构共享世界状态。

**Pros**:
- ✅ 潜在吞吐更高，慢 DB 不会阻塞其他分区
- ✅ 可利用多核做 AI / 战斗结算

**Cons**:
- ❌ 引入锁顺序、死锁、数据竞争等一整类新缺陷
- ❌ 本系统的瓶颈不在 CPU 而在 I/O 与字符串处理，收益有限

**Why Not Chosen**: **已确认** —— 正确性优先于吞吐；世界状态免锁是核心收益，
当前规模下单线程足够。

### Alternative 2: 组件化 / ECS 对象模型替代属性袋

**Description**: 用带类型的组件（`Position`、`Health`、`Inventory`）替代
`query("hp")` 字符串键，用 `dynamic_cast` 之外的机制做能力判定。

**Pros**:
- ✅ 编译期类型安全，重构可被编译器检查
- ✅ 消除热路径上的 `dynamic_cast` 与字符串查找

**Cons**:
- ❌ 序列化不再"整袋即 JSON"，持久化层要重写
- ❌ 脚本侧 `self:query("quest/lilaotou")` 的自由键值访问会受限，脚本作者体验下降
- ❌ 迁移面覆盖 `src/` 全部 17 个子系统

**Why Not Chosen**: `INTENT UNKNOWN — inferred from implementation, not confirmed`。
从代码看属性袋被**有意**保留（`Container.h:5-8` 注释表明非容器行为被主动拆出到接口），
推断为"已评估、选择了自由键值的表达力"，但作者未确认。

### Alternative 3: 异步 DB（连接池 + 写队列）

**Description**: 把 `IDatabase` 调用改为异步：写操作入队批量落盘，读操作走线程池并回投结果。

**Pros**:
- ✅ 消除"慢查询冻结全世界"这一最大可用性风险
- ✅ 自动存档、关服批量存档不再卡顿
- ✅ 为未来水平扩展留出空间

**Cons**:
- ❌ 引入读写时序问题（读己所写），需要显式的完成回调与一致性约定
- ❌ 与"世界状态只被一个线程触碰"的免锁前提冲突，需要重新设计状态交接边界

**Why Not Chosen**: `INTENT UNKNOWN — inferred from implementation, not confirmed`。
已确认的事实是"当前规模下阻塞 DB 被接受"；是否评估过异步方案未获回答。

## Consequences

### Positive Consequences（Benefits Realized）

✅ **免锁正确性**：世界状态只被 `main_worker_thread` 触碰，
"漏加锁导致的数据竞争"这一整类缺陷在世界态上**结构性不可能发生**。
这是本决策最大的收益，也是它被选择的原因。

✅ **内容与引擎解耦**：`lua-sample` / `lua-default` 可热更、可整体替换；
"引擎不知道任务类型"仍能实现任务系统（`lua-sample/data/quest.lua` 挂 `hooks.pre_talk`）；
用户根可覆盖默认根同名脚本，实现服务器差异化。

✅ **确定性与可调试性**：单一游戏线程 + 心跳驱动意味着事件可串行回放；
`g_current_time` 单点刷新，没有跨线程时钟竞态。

✅ **可测试性（真实存在的 seam，非测试专用）**：`IDatabase* g_db` 是生产就在用的
MySQL/SQLite 切换点，测试据此注入 `MockDatabase`/`ThrowingDatabase`
（`tests/unit/mock/mock_database.h`）；`src/db/Sql.cpp` 与 `main.cpp` 被排除出
`jianghu_core.lib`，由 `tests/unit/mock/mock_db.cpp` 链接期替换。

✅ **序列化廉价**：整袋 dbase 直接 `CMapping::get_buffer()` 变 JSON，
新增游戏属性**零持久化代码**。

### Negative Consequences（Trade-offs Accepted）

⚠️ **游戏线程上的阻塞 SQL 是全局停摆点**。
更糟的具体形态：`on_login` 中的 `verify_user` / `load_from_server` / `save`
在**同时持有 `g_gate_list_mutex` 与该 gate 的 `m_cs`** 状态下执行
（`src/net/ServerSockWorker.cpp:142,153`），而 worker 侧 `dispatch_gate_recv`
需要同一把 `m_cs`（`GateRecvDispatch.cpp:19-27`）—— 慢 DB 不只冻结世界，
还会冻结**该连接的收包**。MySQL 连接超时 5 s，但语句**没有超时**。

⚠️ **`g_gate_list` 存在数据竞争**：`push_back`（`ServerSockHandler.cpp:237`）与
erase 循环（`ServerSockWorker.cpp:213-221`）**未加锁**，与已加锁的迭代
（`ServerSockWorker.cpp:142`）并发 —— 锁存在但未覆盖全部访问点。

⚠️ **硬性 32 位约束**：`GateClient.cpp:12-52` 把 `CGateInfo*` 截断成
`uint32_t serial` 当作连接标识；一旦迁到 x64 立即失效，且陈旧 serial 有
use-after-free 隐患（引用计数部分缓解，但 `close_client` 路径不持引用）。

⚠️ **属性袋无类型安全**：`query("hp")` 全靠字符串约定，键名拼错在编译期与运行期都无告警；
`enum` 与字符串键两套寻址方式并存。

⚠️ **热路径上的 `dynamic_cast` 与字符串查找**：每次命令最多 3 次
`dynamic_cast<IActionHandler*>`（`CmdHandle.cpp:226,252,257`）+ 多次字符串 map 查找；
`CContainer::present()` 是容器内容的**线性扫描**（`src/object/ContainerItem.cpp:24-57`），
`find_online` 是 `g_user_list` 线性扫描。

⚠️ **无 schema 迁移、无事务**：`CREATE TABLE IF NOT EXISTS` 是全部 schema 管理；
`db_save_container` / `db_update_recruit` / `sql_update_record` 等是
"先 SELECT 后 INSERT/UPDATE" 的读改写，**只因进程内单写者才成立**，
一旦有第二个进程写库立即产生竞态。`verify_user` 用 `select *` **按下标**取列
（`src/db/Sql.cpp:226-313`），列顺序变化会静默错位。

⚠️ **Lua 层没有安全边界**：`luaL_openlibs` 全量标准库 + `db_execute`/`db_query`/
`os`/`io` 全开（`LuaBind.cpp:277-280`）；对象传给 Lua 是**无 `__gc` 的裸指针 userdata**
（`LuaBind.cpp:19-32`），悬垂只靠单线程纪律兜底。

### Neutral Consequences（Observations）

ℹ️ 单 `lua_State` + 单线程使 `CLuaSkill::query_action` 返回的函数级 `static CMapping`
（`src/lua/LuaSkill.cpp:156`）可用而不产生数据竞争 —— 一旦引入第二模拟线程，此写法立即变成缺陷。

ℹ️ **延迟析构成为全库惯例**：因为 `delete` 被推迟，所有可能触发销毁的回调之后
都必须检查 `g_last_destruct_object == object_id()`；这条不变量没有编译器或断言强制，
只靠约定传播。

ℹ️ **GBK 成为跨层契约**：脚本字面量、C++ 字符串、协议三者统一 GBK；
`LuaRoom.inl` / `LuaNpc.inl` / `LuaItem.inl` 对 `comm/arg/tar/dir` 均原样压栈、
不做转码。历史上 `LuaRoom.inl` 曾单方面转 UTF-8（与字面量反向，靠样本命令均为
ASCII 掩盖），2026-10-24 已统一，契约测试 `tests/unit/test_dispatch_encoding.cpp`。

ℹ️ 关服是**协作式**的：`WM_CLOSE` → `DestroyWindow` → `WM_DESTROY` → 信号 IOCP 退出
→ `wait_for_all_worker_threads(10000)` → `user_release` 批量存档
（`src/main.cpp:170-185`、`src/user/UserMgr.cpp:42-55`）。

## Implementation Notes

**Patterns Used**:

- **Proactor（IOCP）**：网络层；完成事件驱动，不做阻塞 recv。
- **单线程 Actor / 游戏循环 + 生产者-消费者交接**：`CWHQueue` 每连接互斥队列
  把 N 个 I/O 线程与 1 个模拟线程解耦 —— 经典 MUD"网络线程 + 单模拟线程"结构。
- **引用计数跨线程生命周期 + 延迟删除列表**：`CGateInfo` 引用计数（`GateInfo.cpp:16-21`）；
  世界对象走 `g_destruct_list`。
- **表驱动分派 + 链式回落**：三张 C++ 命令表 → Lua `commands[cmd]` 回落；
  频道 / 环境 / 目标拦截层在表之前。
- **模板方法 + Mixin 接口**：`CChar`/`CItem`/`CRoom` 声明虚钩子，`CLua*` 模板包装重写并转发脚本，
  失败回落基类；5 个接口把"非容器行为"从基类拆出。
- **Hook（Strangler 式扩展点）**：25 处 `hooks.*`，缺席即不生效。
- **配置快照**：`init_game` 期把 ini 读进各模块静态成员。

**Dependencies Introduced**:

- Win32 / Winsock2（`winsock2.h`、`AcceptEx`、`WSASend`、IOCP）—— 平台锁定
- `libmysql.lib` + `libmySQL.dll`（`3rd/include/mysql`、`3rd/lib`）
- Lua 5.5（`lua55.lib`，真实链接进测试）
- SQLite（`3rd/sqlite/sqlite3.c`，编进 `jianghu_core.lib`）
- DbgHelp（崩溃时 Lua+C++ 双栈回溯，`LuaEngine.cpp:271-349`）
- Google Test（NuGet，仅 `tests/`）

**Performance Characteristics**:

- 时间复杂度：命令分派 O(命令表查找) + 最多 3 次 `dynamic_cast`；
  `present()`/`find_online` O(n) 线性扫描；心跳 O(活跃对象数)；
  每次 C++→Lua 调用 = `lua_rawgeti` + `lua_getfield` + `lua_pcall`，**函数 ref 不缓存**。
- 空间复杂度：整套结果集物化进内存（`mysql_store_result`，`MySqlDb.cpp:40-88`）；
  两套 dbase 映射常驻；每连接 16 KB recv 缓冲（可用 8 KB）。
- **已知热点**：`load_script()` **在缓存查找之前整文件读盘算 djb2 哈希**
  （`LuaEngine.cpp:666-667`），而 `load_script` 被 `create_*`、
  `get_script_bool_field` 等热路径调用 —— 每次派发的 I/O 放大是脚本层主要开销来源。
- **真正瓶颈**：同步 DB I/O 与字符串处理，不是 CPU。

**Thread Safety**:

- **模型**：模拟层单线程；网络层 N 线程；二者仅通过 4 把锁保护的队列/列表交接。
- **锁清单**：每连接队列 `std::mutex`、`CGateInfo::m_cs`（recursive）、`g_gate_list_mutex`、
  `g_destruct_list_mutex`；另有 `Interlocked*` 用于 gate 引用计数与 `m_do_sending`。
- **世界状态：无锁，且这是设计而非疏漏。**
- 未加锁的访问点见 Consequences 的 `g_gate_list` 条目。

**Testing Strategy**:

- **单元测试**：`tests/unit/tests.vcxproj`，静态库 `jianghu_core.lib` + 链接期 mock
  （`mock_db.cpp`、`mock_itemmgr.cpp`、`mock_net.cpp`、`mock_database.h`）；
  真实 Lua 链接，脚本测试只针对 `lua-default` 与 `lua-sample`。
- **E2E**：`run-integration-tests.ps1` 起真实服务器 + 无头 CLI + **多账号并行的四条道**
  （`register.sce` 先并行注册，再并行跑 `lane_foot` / `lane_skill` / `lane_combat` /
  `lane_social`——每道一个独立账号，`include` 串起各自的剧本片段）。
- **唯一认可的验证入口**：仓库根 `.\run-coverage.ps1`（`Release|Win32`，
  绝对禁止 Debug —— Debug 与 Release 不是同一个被测对象）。
- Coverage：门槛 75% 及格 / 90% 良好；E2E 行覆盖约 33%（缺口是系统性的，由单测兜底）。

**Known Issues**（discovered during analysis）:

- ⚠️ **疑似连接泄漏**：游戏侧主动关闭走 `close_client` 置 `m_login = CLOSING(-1)`
  （`GateClient.cpp:12-23`），而 `RECV_MSG_EXIT` 分支只在
  `m_login > GATE_LOGIN_PENDING_DELETE` 时才进入删除流程（`ServerSockWorker.cpp:175-176`）
  —— 即 `-1` 永远不进删除分支。**未做运行时追踪，需实证。**
- ⚠️ **`[server] ip_limit` 疑似不生效**：ini 值读入 `g_ip_limit`（`GameInit.cpp:95`），
  但登录限流实际读 `g_combat_config.ip_limit()`（`Login.cpp:252,336`），
  其值来自静态默认 30 且只能被巫师命令修改（`CombatConfig.cpp:12-19`）。
- ⚠️ **登录密码变更路径的 SQL 注入面**：`passwd`/`validate` 命令把原始 `arg` 传入
  `db_change_password`（`src/cmd/CmdUserAccount.cpp:176,190,206` → `SqlAccount.cpp:179-181`），
  **不经转义**；登录路径靠整体剥除 `'` 缓解，游戏内路径没有。
- ⚠️ **死代码 / 死配置**：`alarm_loop` 与 `g_heart_beat_flag` 无调用者；
  `SetEvent(g_event)` 指向从未 `CreateEvent` 的句柄；`db_save_box/db_load_box/db_delete_box`
  与 `select_game_database` 只有测试 stub；`t_saveobj`、`user` 表有 DDL 无调用方。
- ⚠️ **`gen_apply.py` 缺失**：`LuaBindDecls.h` 注释称绑定由该脚本生成，仓库中找不到它。
- ⚠️ **`CCmdHandle` 双全局**：`CommandHandle`（`src/char/Char.cpp:32`，实际被用）
  与 `g_command_handler`（`Global.cpp:20`，疑似未使用）。

**Risks**:

- 慢 DB / DB 断连 → 全服冻结（无语句超时、无重连：`m_mysql` 保持非空、后续调用全部失败）。
- 迁 x64 → `uint32_t serial` 立即失效。
- 增加任何第二模拟线程 → 世界态免锁前提瓦解，且已存在 `static` 返回值等隐性依赖。
- 脚本包若为第三方来源 → 无沙箱 + `db_execute` 构成全域读写面。
- `jianghudb` 列顺序一旦变更 → `verify_user` 下标映射静默错位。

## Appendix: Code Snippets

**Key Implementation Pattern** —— 游戏线程主循环（三段式：出队 → 执行 → 心跳）：

```cpp
// src/net/ServerSockWorker.cpp:224-246（节选改写）
DWORD WINAPI main_worker_thread(LPVOID)
{
    while (!g_terminated) {
        process_user_message();   // IOCP 线程塞进来的消息出队并分发
        user_command_loop();      // 串行执行玩家命令（含全部 DB 写）
        if (tick_passed_1000ms())
            call_heart_beat();    // 心跳 + Lua 热更 + 对象真正 delete
        flush_destruct_list();
    }
    disconnect_sql_server();
    return 0;
}
```

**Rationale**: 这段代码就是整个决策的实体 —— 世界状态只被这一个线程触碰，
所以 `g_user_list`、`g_room_list`、`g_heart_beat`、两套 dbase 都不需要任何锁；
而它的代价（DB 阻塞会卡住这里的所有人）也写在 Consequences 里。

**Alternative Approach**（未选择）—— 异步写队列：

```cpp
// 未实现：写操作入队，由独立 DB 线程批量落盘
while (!g_terminated) {
    process_user_message();
    user_command_loop();
    // db_write_queue.push({UPDATE jianghudb ...});  // 不在本线程执行
    call_heart_beat();
}
```

**Why Not**: 已确认"当前规模下阻塞 DB 被接受"；且异步化会破坏
"读己所写"的直观语义与免锁前提，需要重新设计状态交接边界（见 Alternative 3）。
