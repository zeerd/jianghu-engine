# 日志监控（LogMonitor）

`config.ini` 的 `[opencode]` 配置了 `cli_path` 即启用：监控线程发现日志中
新的 WARN/ERROR 级问题 → 调 opencode CLI 分析生成 plan → plan 落盘 →
经飞书自定义机器人 webhook 推给开发者。

## 为什么挂钩 `log_message`，而不是尾随日志文件

- `log_message` 是全引擎日志的唯一出口：行的级别已判定、GBK 已转 UTF-8，
  挂钩拿到的就是最终形态；
- 尾随文件要额外处理读偏移、按日换文件、编码与「哪些算新行」的竞争，
  换来的只是同一批数据的另一条通路；
- 挂钩点在写文件之后：监控自身故障不影响日志落盘。

## 触发模型：信号 + 快照 + 合流

- 挂钩先把行写入**有界环形缓冲**（容量 = `context_lines`），达到阈值的行
  再置触发标志——触发是信号不是逐条队列，不存在「某行被消费掉」的路径；
- **先入缓冲、后置标志**的顺序保证：监控线程见到标志时，置标志的行必然
  已在缓冲中，快照不可能漏掉触发行；
- 线程唤醒后先等**合流窗口**（`flush_ms`）再快照：并发同时落盘的多条
  日志聚齐后一并进入同一轮分析，而不是每个线程各触发一轮；
- 分析期间（opencode 最长跑 `timeout` 秒）到达的日志继续入缓冲并再次置
  标志，回来后下一轮快照自然带上——没有丢弃路径；
- 缓冲溢出丢最旧并计数（`dropped_lines`），日志线程永不被监控阻塞。

## 签名 TTL（同签名去重，默认一天）

- 签名 = 剥掉行首 `[级别] (时间戳) ` 前缀 + 数字串归一化为 `#` +
  参与哈希的级别（FNV-1a 64）。同一处代码抛出的问题（仅 id/计数不同）
  得到同一签名——**签名即问题身份**；
- TTL 表「签名 → 到期时刻」，表上限 4096：先剪过期项，仍超限淘汰最早
  到期的，内存有界；
- 认领发生在分析之前：**分析失败不回收签名**——分析通道坏掉时，同一问题
  不会被反复拉起，故障以 INFO 日志留痕；
- 快照里至少一个新签名才开分析，一轮带出快照中的所有新问题。

## 依赖与失败语义

- `IFeishuSender`（载荷组装 + WinHTTP 传输 + 失败重试一次）与
  `IOpencodeRunner`（命令行拼装 + CreateProcess/超时按自有句柄终止 +
  JSONL 解析）是生产装配的两端：生产在 `log_monitor_start` 装配真实现，
  测试注入假件；
- opencode 以 `run --format json --auto --file <上下文>` 非交互运行：
  `text` 事件拼成 plan，`error` 事件是失败原因；无助手文本即失败；
  日志上下文走附件文件，命令行长度与日志规模解耦；
- plan 落盘 `<log>/plans/M-D-HHmmss-<级别>.md`（与日志文件同用月-日、
  月日不补零）；飞书正文超 28KB 在 UTF-8 边界截断，截断注记里带文件路径；
- 监控链路自身**只记 INFO**：告警不回灌告警，避免自激递归。

## 可观测性

- 监控链路全程 INFO 留痕（INFO 不回灌告警）：启动横幅（参数与 plan
  目录）、分析开始（新签名数 + 上下文路径）、分析完成（耗时 + plan
  绝对路径）、推送结果；进程失败模式在日志里分流为超时 / 取消 / 故障
  三种措辞——「跑太慢」与「没跑起来」不再共用一句话。
- TTL 压制不记日志：冷却期内的重复触发是预期行为，逐条留痕等于把
  刷屏从告警换到 INFO；需要确认去重是否生效时看启动横幅的 cooldown。

## 生命周期

- 路径口径：**配置可相对**（工程整体可挪动），装配时按服务器工作目录
  解析为绝对；**运行期产物出生即绝对**——上下文文件、plan 落盘路径与
  交给子进程的入参都不依赖 cwd（opencode 在 work_dir 下运行，相对路径
  会到那里去找文件）。
- `log_monitor_start` 在 `init_game` 成功后调用；配置写定后不再变更，
  挂钩侧据此做无锁读取与零成本早退；`cli_path` 为空 = 配置即停用；
- `log_monitor_stop` 在 `WM_DESTROY` 最先执行：先取消在途分析再 join，
  否则关机会等满一个分析超时；
- 签名表属监控实例，随进程存续；线程停止后实例可重复 start。
