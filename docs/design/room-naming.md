# 房间名解析合同

> 本文是房间脚本各「名字」之间关系与解析顺序的**权威文档**：名词含义、解析顺序、
> 参与静态判定的引用形态、判定口径与边界。本文与代码冲突时以代码为准，
> 实现位置见 §8（导航，非规范）。

---

## 1. 目的

一个房间同时被三样东西指代：**脚本文件**、**脚本文本里的键**、**玩家看到的字**。
引用写错键时，引擎仍然会返回一个房间（兜底房），因此错误不以报错形式出现，
只表现为「内容缺失 / 走错房间」。本文定义这些名字各自的角色、引用按什么顺序解析、
什么算断链，使脚本作者、静态检查器与运行时共用同一把尺。

---

## 2. 术语

| 术语 | 定义 | 应避免的误用 |
|---|---|---|
| **裸脚本名** | 房间脚本文件名去掉扩展名；引擎按扫描树建索引，**与所在子目录无关** | 不要把它当作显示名 |
| **引用键** | 脚本返回表的顶层 `name` 字段；中文引用靠它反查脚本 | 不要写成显示名 |
| **显示名** | `create` 中 `set_name` 设的字面，玩家看到的字 | 不要拿它当引用键 |
| **动态实例前缀** | 返回表的 `prefix` 字段；命中前缀的未登记房间名由该共享脚本实例化 | 不要理解成通配符 |
| **实例键** | 房间对象运行时的 `base_name` | 普通房 = 引用键；副本房 = 副本实例内的键 |
| **副本内房间键** | 副本实例命名空间下的房间键 | 不要假设它在全局可解析 |
| **过程式房名** | 由脚本按规则生成的房名（坐标 / 序号拼出），不存在静态字面量 | 静态检查看不到它 |

**键与显示名分离是设计的一部分**：引用键负责被找到，显示名负责被读到，
两者可以不同，也可以相同。把显示名当引用键（或反之）才会断链。

### 2.1 示例：各术语在脚本中的位置

```lua
-- ===== A. 一份房间脚本（room/demo/demo_room.lua）=====
-- 【裸脚本名】demo_room —— 文件名去 .lua，与所在子目录无关，引擎按它建索引

return {
    -- 【引用键】中文引用靠它反查到本脚本：load("room", "洛阳城东")
    name = "洛阳城东",

    create = function(self)
        -- 【显示名】玩家看到的字；与引用键是两个东西，改它不改变任何引用的解析结果
        self:set_name("城东")

        -- add_object("door", 门id, 目标房间, 对门的门id [, 方向])
        --                    ↑第2串是门id   ↑第3串才是房间：必须写引用键，写显示名即断链
        self:add_object("door", "西门", "洛阳城西", "东门")
    end,
}

-- ===== B. 共享实例脚本的返回表（只声明前缀、不声明引用键）=====
--     return { prefix = "house_", ... }
-- 【动态实例前缀】凡以此开头且未登记的房间名（如 house_西湖_3）都由本脚本实例化，
-- 被引用的完整名字即该实例的【实例键】：load("room", "house_西湖_3")

-- ===== C. 引用侧（任意脚本 / 配置）=====
load("room", "洛阳城东")                    -- 按【引用键】解析
load("room", "demo_room")                   -- 按【裸脚本名】解析
self:load_fb_room("某某密室")               -- 目标在【副本内房间键】命名空间：
                                            -- 先在本副本实例内按实例键找，查不到静默退化
load("room", string.format("野外%d_%d_%d", n, x, y))
                                            -- 【过程式房名】完整名字只在运行时产生，
                                            -- 没有静态字面量，静态判定看不到它
-- 配置项 start_room = 洛阳城东             -- 配置里的引用同样按【引用键】解析

-- ===== D. 运行时：同一个房间对象的【实例键】base_name =====
--   普通房 = 被解析出的引用键（"洛阳城东"），单例房间表按它缓存
--   前缀房 = 被引用的完整名字（"house_西湖_3"），由 prefix 共享脚本实例化
--   副本房 = 本副本实例内的房间键（"某某密室"），同副本内同键即同实例
```

---

## 3. 解析顺序

### 3.1 普通房（`load("room", X)`、非副本房的门 `next_room`）

1. 运行时单例房间表里已有实例键 `X` → 直接返回；
2. 按**裸脚本名**在脚本表里找 `X`，命中即用该脚本；
3. 按**引用键**（`name` 索引）反查脚本；
4. `X` 命中某共享脚本的 `prefix` 前缀 → 用该脚本实例化，实例键记为 `X`；
5. 内置的副本注册处；
6. 兜底：通用房间 + 读 `t_room`（按实例键取行）；取不到则换成名带 `fail` 前缀、
   标记 `fail_ob` 的标准房间并告警——**引用不达意，但不崩溃**。

### 3.2 副本房（副本总控 `load_fb_room(X)`、副本内的 `CFBDoor` 落点）

1. 先在**本副本实例**内按实例键 `X` 找已有房间（同副本内同名即同实例）；
2. 没有则走与 3.1 第 2–4 步相同的脚本查找；
3. 再没有 → **标准副本房间**，静默退化，不置 `fail_ob`。

### 3.3 两个脚本根

引擎按配置的 `script_root`（内容数据集）与 `default_script_root`（内置默认脚本）建索引，
**默认根在前、内容根在后，同名时内容根覆盖默认根**。
因此默认根下的房间对内容根的引用同样有效。

## 4. 引用形态

**参与静态判定**的字面量引用：

| 形态 | 取哪个字符串 |
|---|---|
| `load("room", "<键>")` | 第 2 参 |
| `add_object("door", "<门id>", "<目标房间>", …)` | **第 3 个字符串**（第 2 个是门 id，不是房间） |
| `load_fb_room("<键>")` | 第 1 参 |
| 配置项 `start_room = <键>` | 整值 |

**不参与静态判定**（原理上取不到完整目标名）：

- 注释行内的引用；
- `"字面量" .. 表达式` 拼接出的动态引用——只登记为动态引用，不判断链；
- 变量传参与 `door:set("next_room", 表达式)` 形式的改绑。

---

## 5. 不变量

- **I1** 每条可静态判定的引用，必须能在两个脚本根之一解析为裸脚本名或引用键，或命中 `prefix` 前缀；否则即断链。
- **I2** 引用键全工程唯一：重名时索引只保留一个，解析落点取决于登记顺序，属歧义。
- **I3** 同一脚本根内裸脚本名唯一；跨根同名是既定覆盖语义（内容根胜），不属缺陷。
- **I4** 显示名不参与解析：改显示名不改变任何引用的解析结果。
- **I5** 普通房解析失败必然落到兜底房（不崩溃、不返回空）；副本房解析失败静默退化为标准副本房间——两者的失败可见度不同。
- **I6** 静态可判定的引用只有 §4 列出的字面量形态，其余形态必须留给运行时。

---

## 6. 边界与非目标

- **不覆盖数据行支撑的兜底房**：实例键只存在于 `t_room`、不在任何脚本里的房间，静态检查原理上看不见。
- **不覆盖非脚本引用源**：除 `start_room` 外的配置 / 数据文件引用。
- **不覆盖过程式房名**：其完整名字只在运行时产生。
- **当前引擎没有「按房名造房」的野外工厂**：过程式野外房名只能落到 3.1 第 6 步兜底。
  这是已知实现缺口，不改变本合同；补齐时应按 I6 一并说明其静态可判定性。
- 本合同不规定房间内容（出口、NPC、文案）的正确性，只规定名字的可解析性。

---

## 7. 键与显示名为何分离（沿革）

原版 C++ 中两者本来就是分开的两套东西：

- **房间键** = 创建时的入参：先匹配特殊名，再按中文前缀派发到区域装载器，在链上用
  `房间键 == "<中文键>"` 精确匹配，之后才是前缀族与数据库兜底；
- **显示名** = `set_name` 设的字面，**常省略区域前缀与序号**。

因此「键 ≠ 显示名」是既有设计而非缺陷；转换或重写脚本时若把显示名写进引用键、
而引用仍按房间键书写，就会成批断链。原版同样存在「只有引用、没有活键」的历史悬空引用
（含被注释掉的派发项），这类引用会被原样继承下来。
