# 江湖客户端-服务端通讯协议规范 v1.0

---

## 1. 传输层与封包格式

### 1.1 传输介质
| 项目 | 值 |
|------|-----|
| 协议 | TCP |
| 端口 | 6600 |
| 字符编码 | GBK（中文简体） |
| 分隔符 | `\t` (0x09, Tab) — 消息边界 |
| 发送块 | 单次发送以 `\t` 结尾；超长消息可能被拆为多个块，客户端应逐块解析 |
| 单条上限 | 单条 C→S 命令不超过 1024 字节，超限服务端丢弃并报错 |

### 1.2 消息格式

#### 服务端 → 客户端
```
&C=<命令码>&<键1>=<值1>&<键2>=<值2>&...&\t
```

- 每条消息以 `&C=N&` 开头，其中 N 为命令码（整数）
- 键值对以 `&` 分隔
- 消息以 `\t` (0x09) 终止
- **整条消息在发送前经 XOR 编码**（见 1.4 节），客户端必须先解码再解析
- `\n` 不会被服务端从命令中剥离，可保留在消息文本内作换行显示

#### 客户端 → 服务端
```
<player_id> <命令> <目标ID> <参数...>\t   # 普通命令（进入命令队列）
0 <命令> <目标ID> <参数...>\t             # 0 前缀=立即执行，绕过命令队列
login ...\t                              # 连接后第一个包（见下方登录认证包）
```

- 消息以 `\t` 终止
- **首字段 `player_id` 必须是 LOGINUSER 返回的玩家对象 ID（`U=`）**：服务端校验其与当前连接的
  玩家一致，不一致则整条命令被**静默丢弃**（无任何回包）
- 第二字段为命令字，第三字段为目标对象 ID（无目标可省略或填 `0`），其余为参数正文
- `0 ` 前缀的立即执行命令不进入命令队列，且**不校验 player_id**
- 整条命令同样经 1.4 节 XOR 编码后发送
- 命令队列深度 20：一次输入过多会收到「对不起，你一次输入的指令太多。」
- 命令频率受限：短时间内发送过多命令会收到警告（`$HIR...第N次警告！`），
  多次警告后角色将被强制进入不可控状态

#### 登录认证包（特殊格式）

**注意：** 连接建立后服务端收到的**第一个包**强制按登录包处理（见第 2 节状态机），
且登录数据必须经 XOR 编码（见 1.4 节）。

登录包原文格式（加密前）：
```
login <客户端本地IP> <客户端版本> <账号ID> <密码> <卡号> <卡密>\t
```
- 共 7 个空格分隔 token（含首词 `login`）
- `<客户端本地IP>`：客户端本机 IP，服务端仅用于连接限制判定，不影响鉴权
- `<客户端版本>`：客户端版本号，服务端记录于会话
- 连接来源 IP 由服务端按 TCP 对端地址自动获取，**不由客户端发送**
- 首词非 `login` 时服务端回复 `&C=19&F=1&M=请到主页注册&\t` 并断开连接

### 1.3 编码处理
- 仅**登录包**在首个 `\n` 处截断；普通命令包只按 `\t` 分包，`\n` 保留
- 客户端收到的消息文本内可含 `\n`，应保留以便多行显示
- 客户端发送的命令参数中的 `&` 会被服务端剔除，参数中不要依赖 `&` 传递信息

### 1.4 XOR 编码（全协议、双向、对称）

**全部**客户端↔服务端消息使用同一把对称 XOR 密钥处理（加密与解密为同一算法）：

- **C→S**：登录包与每一条命令都要编码
- **S→C**：服务端下发的每一条消息（含登录阶段的失败提示）都要编码

**密钥**（14 字节）：
```
0D 4C 16 41 10 4E 0A 57 15 4F 1B 4F 06 44
```
对应的 C 字符串字面量（八进制）：`"\15L\26A\18N\12W\25O\33O\6D"`。

**算法**（收发两侧相同）：
1. 逐字符处理
2. 空格 `' '`、`\n`、`\t` 字节**跳过不处理**（以明文保留，保证分隔符可见）
3. 其余字符与密钥当前字节 XOR；密钥索引每处理一个字符 +1，**每 14 字节回绕**
4. 若 XOR 结果为 `\t`、`\n`、空格或 `\0`，则用同一密钥字节**再 XOR 一次**（安全回退，规则自逆）

## 2. 连接状态机

| 值 | 状态 | 说明 |
|-----|------|------|
| 0 | 未登录 | 刚建立 TCP 连接；收到的**首包**按登录包处理 |
| 1 | 正在登录 | 已收到登录包，验证中；此后的包在验证完成前被丢弃 |
| 2 | 游戏中 | 登录验证通过，命令按 `\t` 分包正常处理 |
| -1/-2/-3 | 断开中 | 正在断开/释放连接，客户端应视为连接已结束 |

> 客户端只需区分「未登录 → 登录中 → 游戏中」三阶段；负值为服务端断开过程的细分，
> 客户端观察到的是 TCP 连接关闭。

## 3. 登录流程

### 3.1 完整登录序列

客户端在建立 TCP 连接后的完整通信流程：

```
步骤         方向          消息内容                              说明
――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――――
1.  C→S     login <本地IP> <版本> <id> <passwd> <card> <cardpass>\t  登录请求（7字段，XOR编码）
2.  S→C     &C=18&F=1&M=<错误信息>&\t                           登录失败（可选，见 3.3）
  或
2.  S→C     &C=10&R=<房间>&I=<地图>&N=<房间名>&F=<战斗标志>&D=<入口方向>&\t  切换房间(GOTOROOM)
3.  S→C     &C=24&R=0&\t                                        出口段结束标记(ADDOOR)
4.  S→C     &C=24&R=<房间>&D=<方向>&N=<目标房名>&A=<标签>&\t      逐出口条目，每出口一条
5.  S→C     &C=18&U=<oid>&G=<权限>&V=<版本>&R=<运行时长>&
                 M=<服名>&l=<剩余点卡>&Y=<月卡月数>&\t           登录成功ACK(LOGINUSER)
6.  S→C     &C=30&B=1&\t                                         公告开始(BULLET)
7.  S→C     &C=30&M=<公告文本>&\t...(多行)                        公告行
8.  S→C     &C=15&T=<oid>&o=...&\t                               角色属性(RTNINFO)
9.  S→C     &C=13&T=<oid>&S=<技能>&L=<等级>&...&[B=1/E=1]&\t      技能列表，每技能一条(RTNSKILL)
10. S→C     &C=23&T=<id>&sta=..&hp=..&att=..&\t                   私发完整状态(STATE)
11. S→C     &C=11&E=<oid>&T=<物品>&U=..&i=1&\t                    背包物品(ADDOBJECT)
         S→C     &C=17&O=<物品>&...&\t                                 详情(DOWNOBJECT)
         S→C     &C=32&T=<物品>&bx=...&\t                              位置(LOCATION)
         ...（每件携带物循环 11→17→32）
12. S→C     &C=14&B=0&T=<oid>&I0=...&\t                          装备列表(RTNITEM)
13. S→C     &C=19&M=$HIG上次连线...\t                            上次登录IP与时间(NOTIFY)
14. S→C     &C=19&M=$HIG本次连线...\t                            本次登录IP与时间(NOTIFY)
15. S→C     &C=19&M=$N连线进入这个世界。\t                        进入世界播报(NOTIFY)
16. C→S     loc 0 <x> <y>\t                                     客户端定位并结束 loading（必发）
17. S→C     &C=11&E=<房间>&T=<对象>&...&\t                        房间内对象逐个下发
         S→C     &C=17&O=<对象>&...&\t + &C=32&T=<对象>&...&\t          详情与位置
18. S→C     &C=21&e=<表情名>&\t...(每个表情)                      表情下载(DOWNEMOTE)
19. S→C     &C=19&M=<欢迎/系统/频道等消息>&\t                     后续通知
```

握手规则：
- **GOTOROOM 后服务端进入装载状态（loading）**：房间内既有对象暂不下发，
  且该玩家除 `loc`/`mv`/`downloadobject`/`downloadskill`/`downloaduser` 外的命令一律被丢弃。
- 客户端解析完地图后必须发送 **`loc 0 <x> <y>`**（target_slot=0，参数为出生坐标）以结束装载；
  此后服务端才开始互相下发房间内对象（步骤 17）。
- 成功 ACK(LOGINUSER) 发生在 GOTOROOM **之后**：下发顺序为
  `10 → 24(R=0) → 24×N → 18 → 30 → 15 → 13×N → 23 → (11/17/32)×背包 → 14 → 19×N → [客户端 loc] → 11/17/32×房间 → 21×N`。
- 重复登录（同帐号已在线）会先向旧连接发 NOTIFY「有人从别处…取代了你」并断开旧连接，后续序列相同。

### 3.2 注册流程（不提供）

协议**不支持客户端注册**：

- 连接后首个包若首词不是 `login`，服务端回复 `&C=19&F=1&M=请到主页注册&\t` 并直接断开
- 账号需通过其他渠道（如主页）申请后再登录

### 3.3 登录失败消息

登录阶段失败由服务端直接下发（同样经 XOR 编码）。主要格式 `&C=18&F=1&M=<错误信息>&\t`；
档案不存在与账号到期两类用 NOTIFY(19)：

| 场景 | 命令码 | 错误信息（中文原文） |
|------|--------|---------------------|
| 首包不是 login | 19 | 请到主页注册（随后断开） |
| 用户不存在/密码错误 | 18 | 您的密码不正确！（两种情况返回同一文案，不区分原因） |
| 帐号被冻结 | 18 | 对不起，此帐号停止使用！ |
| 该地址连接数超限 | 18 | 对不起，该地址被限制为不得登陆超过%d个帐号！ |
| 跨服在线 | 18 | 对不起，该用户现在%d号服务器上！ |
| 在线人数超限 | 18 | 对不起，游戏限制为%ld，请稍候再连。 |
| IP 声誉封禁 | 18 | 对不起，您所在的地址在江湖中的声誉被破坏！ |
| 档案不存在 | 19 | 对不起，您的档案不存在，请重新申请。 |
| 账号到期（开启收费时） | 19 | $HIY您的账户已于 %s 到期，请联系巫师续费。（随后角色被移入新手房） |

## 4. 命令系统

### 4.1 Wire Format — Target Slot

#### Wire Format

从客户端到服务器的完整报文格式为：

```
<player_id> <command> <target_slot> <message>\t
```

| 字段 | 说明 |
|------|------|
| `player_id` | 登录后的玩家对象 ID（LOGINUSER 的 `U=`）。服务端校验其与当前连接玩家一致，否则整条命令被丢弃 |
| `command` | 命令字（如 `tell`, `look`, `say` 等），按字面精确匹配，惯例使用小写 |
| `target_slot` | 目标对象 ID。有目标时必填；无目标命令（`save`、`who` 等）可省略或填 `0`。若正文以对象 ID 开头而漏填本槽，ID 会被误当作 target 消费 |
| `message` | 消息正文（可含任意空格分隔的 token） |

完整示例：

```
"29702 chat 1382 aaa bbb\t"     ← 有目标（闲聊对某玩家发）
"29702 chat 0 ccc ddd\t"        ← 无目标（公开聊天，必须有 target_slot=0）
"29702 look\t"                   ← 无参命令（target_slot = 0，message 为空）
"29702 tell 1382 hello\t"       ← tell 命令（受话者为 1382）
```

#### `command()` — wire format builder

| 调用 | Wire Format |
|------|-------------|
| `command("look", {})` | `"29702 look\t"` (target_slot=0) |
| `command("chat", {"1382","aaa bbb"})` | `"29702 chat 1382 aaa bbb\t"` |
| `command("tell", {"1382","hello"})` | `"29702 tell 1382 hello\t"` |

#### 服务端解析规则：

1. 去掉首字段 `player_id`（校验用，非命令内容）；`0 ` 前缀包为立即执行，跳过校验与队列
2. 剩余部分按空格切分：首词为 `command`，次词为 `target_slot`（转数字，缺省为 0），其余为 `message`
3. 命令字与频道名、表情名冲突时的检索顺序见下

#### 命令检索顺序：

1. **房间/对象钩子**：目标对象（或所在房间）可截获并处理任意命令（如商店的 `list`/`buy`/`sell`）
2. **频道**：命令字命中频道名则作为频道发言处理（见 4.5）
3. **标准命令表**（4.2）— 基础动作
4. **用户命令表**（4.3）— 需权限 grant ≥ 30
5. **巫师命令表**（4.4）— 需 grant ≥ 50，且达到逐条最低权限
6. **扩展命令**：服务端可由脚本动态扩展命令字，未命中内置表时逐个尝试
7. **表情**：命令字命中表情名则作表情动作处理
8. 全部未命中：若执行过程中有失败原因，回 `&C=29&F=<命令字>&M=<原因>&`；
   否则回 NOTIFY「未知的命令。」

### 4.5 频道与隐式命令

以下命令字不属内置命令表：

**频道**：命令字 = 频道名，格式同 4.1（`<player_id> <频道名> <目标ID> <消息>\t`）。已开通频道：
`chat`（闲聊）、`ad`（交易）、`noise`（市井）、`rumor`（谣言）、`party`、`corps`、
`f1`–`f4`、`new`（新手）、`answer`（考试）、`sys`/`news`/`wiz`（需相应权限）。
- `*` 后缀表示表情式发言，如 `chat* 招手`；部分频道不支持表情
- `rumor` 为匿名频道（20% 概率暴露发言者）；`sys`/`news`/`wiz` 需巫师权限
- `party` 与组队命令同名，按 4.1 检索顺序频道层优先判定；组队功能请使用 `accept_party` 等命令

**对象钩子命令**：目标为商店 NPC 时可用 `list <页码>`（每页10件，返回 SENDTABLE 37）、
`buy <商品ID>`、`sell <物品ID>`。

**表情**：表情名可直接作为命令发送（`<player_id> <表情名> <目标ID>\t`），登录时由
DOWNEMOTE(21) 下发可用表情列表。

## 6. 消息格式详细定义

### 6.1 GOTOROOM (10) — 切换房间
```
&C=10&R=<房间对象ID>&I=<地图名>&N=<房间名>&F=<战斗标志>&D=<入口方向>&
```
- **R**: 目标房间的对象ID（LONG整数）
- **I**: 地图名称（如 "起始之间"、"莫愁林"）
- **N**: 房间显示名
- **F**: 战斗标志，1=战斗房间（场景中不可移动），0=普通房间
- **D**: 初始入口方向（如 "east"、"south"、"enter" 等），取自房间配置的初始出口方向

> 注意：发送 GOTOROOM 后服务端进入装载状态（loading）：房间内既有对象暂不下发，
> 该玩家除 `loc`/`mv`/`download*` 外的命令被丢弃；客户端必须发送 `loc 0 <x> <y>`
> 结束装载（见 3.1 握手）。

### 6.2 ADDDOOR (24) — 出口信息
```
&C=24&R=<房间ID>&D=<方向关键字>&N=<目标房间名>&A=<方向标签>&
```
- **R**: 房间ID，与当前 GOTOROOM 的房间一致时有效
- **D**: 方向关键字（如 "north"、"south"、"east"、"west"、"enter"）
- **N**: 目标房间显示名
- **A**: 方向显示标签（如 "正北"、"南方"）
- 发送顺序：GOTOROOM 之后先发**终止标记 `&C=24&R=0&`**，随后逐出口发送条目
  （即 R=0 不在末尾，客户端不应期待其作为结束符出现在条目之后）
- 客户端可按 R 与 GOTOROOM 的房间匹配后收集出口

### 6.3 ADDOBJECT (11) — 添加对象到容器/场景
```
&C=11&E=<环境ID>&T=<目标ID>&U=<更新标志>&[状态字段]&[i=1&][u=1&]
```
- **E**: 环境（容器）对象ID
- **T**: 被添加的对象ID
- **U**: 对象更新标志（数值）；判断玩家请用 `u=1`，不要用 U
- **i=1**: 该对象是物品/尸体
- **u=1**: 该对象是玩家
- **状态字段**（仅角色对象附带，与 STATE (23) 相同）：
  `tea=`/`ap=`/`sta=`/`dis=`/`exe=`/`net=`/`poi=`/`idl=`（见 6.16）

发送时机：角色进入房间、物品加入容器时。添加后通常紧跟 DOWNOBJECT(17) 与 LOCATION(32)（见 6.6）。

### 6.4 REMOVEOBJECT (12) — 从容器移除对象
```
&C=12&E=<环境ID>&T=<目标ID>&
```
- **E**: 环境对象ID
- **T**: 被移除的对象ID

### 6.5 DOWNOBJECT (17) — 下载对象详细信息
```
&C=17&O=<对象ID>&N=<名称>&I=<内部ID>&P=<图标>&a=<数量>&U=<更新标志>&W=<重量>&
   [bx=<x>&by=<y>&ex=<x>&ey=<y>&dr=<朝向>&ac=<活动参数>&]
   [g=1&][x=1&][l=<上锁原因>&][v=1&][b=1&][bk=1&][m=1&][f=1&][w=<装备位>&]
   t=<称号>&[F=1&TA=<队伍A>&TB=<队伍B>&]
```
- **O**: 对象ID
- **N**: 名称
- **I**: 内部ID（如 `fight_room`）
- **P**: 图标编号
- **a**: 数量（堆叠物品）
- **U**: 对象更新标志
- **W**: 重量
- **bx, by, ex, ey**: NPC 活动包围盒（仅 NPC）
- **dr**: 朝向（数值）；**ac**: 活动参数（数值）
- **t**: 称号/标题（始终存在）
- 标志位（存在即为真）：`g`=可拾取，`x`=容器/箱子，`l=<原因>`=上锁，`v`=商人，
  `b`=银行，`bk`=可读书，`m`=可拜师对象，`f`=可使用，`w=<装备位>`=可装备（值见第7节）
- **F=1, TA=..., TB=...**: 战斗房间专用，TA/TB 为两队成员名列表（`Team 0:`/`Team 1:` 开头）

### 6.6 ADDOBJECT (11) + DOWNOBJECT (17) 跟随模式
对于房间中的每个对象（NPC/玩家/物品），服务端按序发送：
1. `&C=11&E=<房间ID>&T=<对象ID>&...&`（添加到房间）
2. `&C=17&O=<对象ID>&...&`（对象详细信息）
3. `&C=32&T=<对象ID>&bx=..&by=..&ex=..&ey=..&ac=..&`（对象位置）

### 6.7 LOGINUSER (18) — 登录响应
#### 成功：
```
&C=18&U=<玩家对象ID>&G=<权限等级>&V=<版本号>&R=<运行时长>&
       M=<服务器名>&l=<剩余点数>&Y=<月卡月数>&
```
- **U**: 玩家对象ID（所有后续命令中代表当前玩家）
- **G**: 权限等级/grant（0=普通玩家，数值越高权限越大）
- **V**: 游戏版本号
- **R**: 服务器启动至今的运行时长（秒）
- **M**: 服务器名称（如 "烟雨江湖"）
- **l**: 剩余点数×10（如 `l=10` 表示 1 点；该字段恒为 0）
- **Y**: 月卡剩余月数

#### 失败：
```
&C=18&F=1&M=<错误信息>&
```

### 6.8 NOTIFY (19) — 通知消息
```
&C=19&M=<消息内容>&
```
- **M**: 消息文本。可包含颜色控制代码（见第8节）

这是最常用的消息类型，用于：
- 聊天消息显示
- 系统提示
- 战斗信息
- 场景描述
- 广播

多个消息可以批量发送。

### 6.9 NOTIFY_FAIL (29) — 命令失败通知
```
&C=29&F=<失败命令>&M=<失败原因>&
```
- **F**: 失败的命令字
- **M**: 错误描述

### 6.10 BULLET (30) — 公告
起始行：
```
&C=30&B=1&
```
公告内容行：
```
&C=30&M=<公告文本>&
```
- `B=1` 表示公告开始
- 公告内容按行分别发送，每条为独立 `M=...` 消息

### 6.11 RTNINFO (15) — 角色详细属性
```
&C=15&T=<目标ID>&
   o=<账号ID>&p=<名字>&P=<头像>&q=<性别>&r=<职业>&s=<种族>&t=<称号>&
   u=<当前负重>&v=<最大负重>&
   exp=<有效战斗经验>&nex=<升到下一级所需经验>&sk=<技能经验>&
   master=<师傅名>&
   a=<年龄>&b=<等级>&c=<声望>&d=<战斗经验>&
   e=<气血>&f=<内力>&g=<最大气血>&h=<最大内力>&i=<有效气血>&
   m=<pk胜场>&n=<pk败场>&
   E=<力量>&F=<体质>&G=<智力>&H=<敏捷>&
   I=<攻击>&J=<伤害加成>&K=<防御>&L=<护甲加成>&
```
- 属性字段使用**单字母键**（a..n、E..L），无 `str=`/`hp=` 等长名键
- exp 为扣除学习消耗后的有效经验；nex 为下一级差值
- I/J/K/L 由当前武器与技能实时计算；J/L 为装备/状态附加值

这是一个非常丰富的属性消息，包含角色的几乎所有可公开属性。

### 6.12 RTNITEM (14) — 物品列表
```
&C=14&B=<批次>&T=<用户ID>&I0=<物品ID>&[E0=<装备位>&]I1=...&
```
- **B**: 批次号。首包 `B=0`，此后每 10 件换一个新包，批次号为该包首件的全局序号
- **T**: 用户ID
- **I0..IN**: 物品ID（第0..N个装备）
- **E0..EN**: 装备位（见第7节装备位置枚举）；**仅当该物品已装备时才携带**，值为装备位编码

### 6.13 RTNSKILL (13) — 技能列表
```
&C=13&T=<目标ID>&S=<技能名>&L=<等级>&[P=<潜力点数>&][M=<激发技能>&][K=1&]
```
- **S**: 技能名称
- **L**: 技能等级
- **P**: 学习所需潜力点数（仅当目标是自己时发送）
- **M**: 当前激发的技能名（mapped skill）
- **K**: 准备标志，`K=1` 表示该技能已准备（prepared）
- **B=1**: 附加在第一个技能包上（列表开始）
- **E=1**: 附加在最后一个技能包上（列表结束）
- 每个技能发送一条独立的 RTNSKILL 消息

### 6.14 DOWNSKILL (16) — 技能基础信息下载
```
&C=16&S=<基本技能名>&N=<显示名>&P=<图标>&E=<所属技能>&[s=1&]
```
- **S**: 技能标识（base_name）
- **N**: 技能显示名称
- **P**: 图标编号
- **E**: 所属基础技能（如 "force", "dodge"）
- **s**: 特殊标志，`s=1` 为特殊技能

### 6.15 DOWNMAGIC (28) — 法术下载
```
&C=28&S=<技能>&M=<法术名>&N=<法术显示名>&R=<内力消耗>&A=<气消耗>&T=<目标>&V=<有效>&
```
- **S**: 所属技能名
- **M**: 法术标识（base_name）
- **N**: 法术显示名称
- **R**: 每次施展消耗内力点
- **A**: 每次施展消耗气点
- **T**: 目标类型
- **V**: 有效性标志

发送时机：每个 DOWNSKILL 之后紧跟着发送该技能下的所有法术。

### 6.16 STATE (23) — 角色状态更新
```
&C=23&T=<目标ID>&[tea=1/-1&][ap=N&][sta=N%&][dis=<状态>&][exe=1&][net=1&][poi=1&][idl=1&]
   [hp=N&mp=N&eh=N&mm=N&att=N&def=N&jl=N&]
```
- **T**: 目标ID
- **tea**: 战斗团队状态，`1`=战斗中且有队伍；`-1`=**非战斗**；缺失=战斗中无队伍
- **ap**: 当前气值（AP，仅战斗中有值）
- **sta**: 血量百分比（0-100，`hp * 100 / max_hp`）
- **dis**: 强制状态文本（如「昏迷不醒」，存在即处于不可控状态）
- **exe=1**: 打坐中；**net=1**: 掉线挂机中；**poi=1**: 中毒；**idl=1**: 发呆超时（非战斗）
- **hp**: 当前气血；**mp**: 当前内力；**eh**: 有效气血；**mm**: 最大内力
- **att**: 攻击力；**def**: 防御力；**jl**: 内力加力值（仅加力后携带）
- 私发完整包（登录、状态变化时发给本人）包含 hp..def；
  广播给房间内其他玩家的是精简包，只含 tea/ap/sta/dis 等标志字段

### 6.17 LOCATION (32) — 对象位置
```
&C=32&T=<目标ID>&bx=<x>&by=<y>&ex=<x>&ey=<y>&ac=<活动参数>&
```
- **T**: 目标对象ID
- **bx, by**: 起始坐标
- **ex, ey**: 结束坐标
- **ac**: 活动参数（与 DOWNOBJECT 的 ac 同义；玩家对象的值由 `mv` 命令上报）

### 6.18 SENDUSER (25) — 用户上线通知
```
&C=25&O=1&U=<用户ID>&
```
- **O**: 固定为 1（上线）；下线不发此消息，玩家下线由房间 ADDOBJECT 移除与 NOTIFY 文本体现
- **U**: 用户ID（当前仅登录时向本人发送自身上线标记）

### 6.19 USERLIST (33) — 在线列表
```
&C=33&N=<注册数>&i0=<ID0>&i1=<ID1>&...&iK=<IDK>&n=<在线数>&
```
- **N**: 消息头部携带的服务端用户表总数（含掉线未清理条目，仅供参考）
- **i0..iK**: 本页用户对象ID列表（`who` 命令分页，每页10人，按上线倒序）
- **n**: 消息尾部携带的实际在线人数

### 6.20 DOWNUSER (34) — 用户信息下载
```
&C=34&U=<用户ID>&N=<名字>&I=<用户UID>&r=<等级>&t=<称号>&
```
- **U**: 用户ID
- **N**: 显示名称
- **I**: 用户UID（账号ID）
- **r**: 等级/权限
- **t**: 称号/标题

### 6.21 DOWNEMOTE (21) — 表情下载
```
&C=21&e=<表情名>&
```
- **e**: 表情名称
- 每个表情一条消息，在登录时批量发送

### 6.22 商店货物列表

商店货物列表经 SENDTABLE(37) 下发：

1. 对商店 NPC 发送 `list <页码>`（页码从 0 起，每页 10 件，见 4.5）
2. 服务端以 SENDTABLE(37)（见 6.23）返回，表名 `vendor`，每行键为：
   `good`（物品代码）、`name`（物品名）、`value`（价格）、`amount`（库存）
3. 价格为整数（进价上浮 20%）；购买 `buy <商品ID>`，出售 `sell <物品ID>`，
   成功后服务端自动重新下发当页列表

### 6.23 SENDTABLE (37) — 表格数据
```
首行:  &C=37&st=1&T=<表名>&R=<参数R>&P=<参数P>&<键1>=<值1>&...
中间行: &C=37&<键>=<值>&...
末行:  &C=37&st=2&...
单行:  &C=37&st=3&T=<表名>&R=<参数R>&P=<参数P>&...
```
- **st**: 段标记 — `1`=起始段, `2`=结束段, `3`=唯一段（既是开头又是结尾）；中间行无 st
- **T**: 表名（如 "vendor"），仅首段携带
- **R / P**: 由表的语义决定，客户端按表名解释；商店（vendor）场景下 R=`总行数×10+页码`，
  P=商店类型
- 表格行数据的键值对跟在段标记之后，每行一条独立消息

### 6.24 WAKEUP (20) — 唤醒（服务端从不下发）

命令码保留但服务端从不发送；唤醒表现通过 NOTIFY(19) 文本与 STATE(23) 更新呈现。

### 6.25 COMMON_ATTACK (22) — 普通攻击
```
&C=22&A=<攻击者ID>&V=<目标ID>&S=<目标血量%>&m=<攻击者内力>&D=<伤害>&
   ap=<攻击者AP>&T=<攻击类型>&M=<战斗文本>&
```
- **A/V**: 攻击者/目标对象ID
- **S**: 目标剩余血量百分比；**m**: 攻击者当前内力
- **D**: 本次伤害数值；**ap**: 攻击者当前 AP
- **T**: 攻击类型字符串（武器技能类型）
- **M**: 战斗描述文本（含颜色码与 `$N`/`$n` 占位，按第8节渲染）
- 发送给房间内可见的玩家

### 6.26 TELLOBJECT (31) — 对象私聊
```
&C=31&i=<发送者账号ID>&n=<发送者名字>&M=<消息>&
```
- **i / n**: 发送者账号ID与显示名
- **M**: 私聊消息文本
- 发给受话玩家本人；发送者自己的回显走 NOTIFY(19)

### 6.27 MAGICCAST (35) — 施法效果（服务端从不下发）

命令码保留，施法表现通过 NOTIFY(19) 与 COMMON_ATTACK(22) 文本呈现。

### 6.28 SYN_AP (36) — 同步气(AP)（服务端从不下发）

AP 值随 STATE(23) 的 `ap=` 字段与 COMMON_ATTACK(22) 的 `ap=` 字段下发，本命令码保留未用。

### 6.29 CONTROLNPC (38) — 控制NPC（服务端从不下发）

命令码保留未用。

### 6.30 ADDLOG (39) — 添加日志（服务端从不下发）

命令码保留未用。

### 6.31 QUESTION (27) — 提问/菜单
```
菜单开始:   &C=27&N=<对象ID>&e=1&
菜单项:     &C=27&N=<对象ID>&s=<显示文本>&c=<选中执行的命令>&[b=1&]
NPC说话:    &C=27&N=<对象ID>&n=<说话者名>&m=<文本>&
```
- **N**: 发起提问/菜单的对象ID
- **e=1**: 菜单开始标记，随后逐条下发菜单项
- **s / c**: 菜单项显示文本与选中后客户端应发送的命令串；`b=1`: 该项为当前已选中项
- **n / m**: NPC 说话时的说话者名与文本（`look`/`talk` 等交互常见）
- 菜单项通过 `look` 或 NPC 交互触发下发；选中项直接作为命令发送即可

## 7. 装备位置枚举

用于 RTNITEM (14) 消息中的 `E<索引>` 字段。每个整数对应一个装备槽位：

| 编码 | 宏名称 | 槽位说明 |
|------|--------|----------|


## 9. 客户端命令格式速查

### 9.1 通用格式
```
<player_id> <命令字> [目标ID] [参数1] [参数2] ...\t
```
- 命令字按字面匹配，惯例使用小写；参数间以空格分隔
- `player_id` 必须为本人对象 ID（LOGINUSER 的 `U=`）
- `0` 前缀为立即执行命令（绕过队列，不校验 player_id）

### 9.2 常见命令示例
（省略了开头的 `<player_id>`，实际发送时必须携带；`0 ` 前缀示例除外）
```
look\t                          # 查看当前房间
look <对象ID>\t                  # 查看特定对象
go east\t                       # 向东移动
get <物品ID>\t                   # 拾取
wield <物品ID>\t                 # 装备
say 大家好！\t                    # 说话
tell <玩家ID> hello\t            # 私聊
kill <目标ID>\t                  # 攻击
halt\t                          # 停止
learn <师傅ID> <技能名>\t         # 学习技能
buy <商品ID>\t                   # 购买（在商店中，目标为商店NPC）
party <目标ID>\t                 # 邀请组队
loc 0 <x> <y>\t                 # 登录后定位，结束装载（必发）
mv 0 <bx> <by> <ex> <ey> <ac>\t # 同步地图坐标
downloadskill <技能ID>\t         # 请求下载技能详细信息
who\t                           # 在线列表
0 save\t                        # 立即保存（不进入队列）
```

## 10. 第三方客户端实现指南

### 10.1 连接建立
1. 建立 TCP 连接到 `服务器:6600`
2. 构造登录包（7 字段空格分隔，见 1.2 节），经 XOR 编码（见 1.4 节）后作为首包发送
3. 按 3.1 序列接收登录数据；收到 GOTOROOM 后渲染地图并发送 `loc 0 <x> <y>` 完成握手
4. 进入命令循环（所有 C→S 命令同样经 XOR 编码）

**重要：** 所有消息（登录与游戏命令、双向）都经同一 XOR 密钥处理，客户端收发都必须编/解码。
本版本协议不支持客户端注册（见 3.2）。

### 10.2 消息解析注意事项
- TCP 流按 `\t` 分割为独立消息；超长消息可能被拆为多个块，逐块解析
- 每条 S→C 消息先按 1.4 节 XOR 解码，再按 `&C=N&` 识别类型
- 之后以 `&` 为分隔符提取键值对；注意部分键为单字母（如 RTNINFO 的 a..n、E..L），按本规范取值，勿臆测语义
- 消息文本内的 `\n` 应保留以便多行显示
- 未知命令码或未知键：忽略即可，协议允许前向扩展
- 加载地图期间（GOTOROOM 之后、`loc` 之前）除白名单命令外的服务端静默丢弃属正常行为

### 10.4 状态管理
客户端应维护以下状态：
- **玩家对象ID**: LOGINUSER 响应中的 `U=` 字段
- **当前房间ID**: GOTOROOM 中的 `R=` 字段
- **房间内对象列表**: 通过追踪 ADDOBJECT/REMOVEOBJECT 维护
- **装备/技能/属性**: 通过 RTNINFO/RTNITEM/RTNSKILL 维护

### 10.5 心跳/断线检测
代码未发现显式的心跳包机制。客户端应自行实现 TCP keepalive 或定期发送检查命令（如 `look\t`）并设置超时检测。

### 10.6 协议局限
- 20/26/35/36/38/39 号命令码服务端从不下发（见 5.1）
- 战斗动画和效果主要通过 NOTIFY(19) / COMMON_ATTACK(22) 文本呈现，客户端按文本渲染即可
- 无二进制或 protobuf 等结构化协议——全部为文本 `&=KV` 格式
